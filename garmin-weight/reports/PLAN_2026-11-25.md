**M8 근거.** EWMA는 첫 측정 뒤로 매일 값을 잇는다(`compute_ewma`). 그래서 28일 창의 최소 14점 조건은 첫 측정 후 약 13일이 지나면 항상 충족되고, 공백이 길어도 다시 깨지지 않는다. 감량률이 `None`이 되는 것은 처음 13일뿐이다. 지금 코드는 그 기간에 추세 표시는 7일 기울기("감량 중 0.32kg/주")로, 예측은 감량률 0(평평)으로 내서 서로 맞지 않는다. 실제 CSV에서 기준 시점마다 이력을 최근 N일만 남기고 예측 방식별 MAE(kg)를 비교했다. 표본은 129~208개이고, 스크립트는 세션 스크래치에만 있다.

| 남긴 이력 | 예측 기간 | 평평(EWMA 수준) | 짧은 창 기울기 | 기울기 × 0.5 |
|---|---|---|---|---|
| 7일 | 14일 / 28일 / 84일 | 0.656 / 0.731 / **1.161** | 0.640 / 0.962 / 2.815 | 0.611 / 0.742 / 1.686 |
| 13일 | 14일 / 28일 / 84일 | 0.657 / 0.734 / **1.131** | 0.593 / 0.831 / 2.091 | 0.605 / 0.709 / 1.404 |

짧은 창 기울기는 1~2주 예측에서는 평평한 예측과 비슷하거나 낫다. 그러나 1개월에서는 나빠지고 3개월에서는 2배 가까이 나빠진다. 화면의 핵심 수치가 1개월·3개월이므로 평평한 예측을 대체값으로 쓴다. 다만 이 기록은 대부분 유지기(84.2kg → 84.1kg)라서 평평한 예측에 유리한 표본이라는 점을 감안해야 한다.

**함께 드러난 점.** 화면은 3개월(84일) 예측을 보여 주지만 백테스트는 7/14/28일만 평가한다. 위 실험에서는 전체 이력으로 계산한 선형 외삽조차 84일 MAE가 1.84kg으로, 평평한 예측(약 1.15kg)보다 나빴다. 운영 모델은 감쇠 곡선이라 수치는 다를 수 있다. P6에서 84일 기간을 백테스트에 넣고, P7의 곡선 선택 기준에도 포함한다.

## 2. 진행 원칙

- **패키지 하나에 브랜치 하나.** 평소처럼 로컬에서 `main`에 머지하고 푸시한다. 푸시 직전에 `git pull --rebase`로 봇 커밋을 받는다.
- **데이터 파일은 커밋하지 않는다.** `data/daily_metrics.csv`와 `data/summary.json`은 봇이 하루 2회 커밋한다.
- **생성 결과를 비교한다.** 패키지를 시작할 때와 끝낼 때 각각 `python garmin-weight/scripts/sync_garmin.py --skip-garmin --output-summary <스크래치>/before.json`(끝낼 때는 `after.json`)을 실행해 둘을 비교한다.
  - 모델과 무관한 패키지: `generatedAt`과 새로 추가한 필드 말고는 같아야 한다.
  - 모델 패키지: 바뀐 주요 수치를 커밋 메시지에 적는다.
- **Garmin 호출을 바꾸면 러너에서 확인한다.** probe 브랜치를 쓴다(P3에서 만든다). 로컬 성공만으로는 부족하다.
- **공개 로그에 값을 남기지 않는다.** 엔드포인트 이름, 예외 클래스, HTTP 상태만 남긴다. 예외 문자열에는 표시 이름이 든 URL이 섞일 수 있으므로 남기지 않는다. 응답 구조를 덤프할 때는 키와 타입만 남기고, 기기 ID처럼 숫자나 ID 형태인 키는 `<id>`로 바꾼다.
- **긴 backfill은 P3(S3 필드 병합) 머지와 D1 판정이 모두 끝난 뒤에만 한다.**
- **로컬 테스트 환경.**
  - unittest는 저장소 루트에서 `PYTHONUTF8=1`로 돌린다.
  - Playwright는 시스템 Chrome을 쓴다(`BROWSER_EXECUTABLE=C:/Program Files/Google/Chrome/Application/chrome.exe`). 서비스 워커 확인 방법은 리포트 11장을 따른다. 테스트에 저장소의 실제 데이터 파일을 쓰지 않는다.

> - **키 시크릿 이름.** 사용자가 새 시크릿 대신 `GARMIN_TOKENS`에 키를 넣었다고 알려 왔다(2026-11-25). 그래서 워크플로는 `secrets.GARMIN_TOKENS`를 셸 스텝의 `GARMIN_TOKEN_KEY` 환경 변수로만 넘겨 암호화·복호화에 쓰고, Python에는 넘기지 않는다. 코드는 `GARMIN_TOKENS`, `GARMIN_TOKENS_JSON`, `GARMIN_MFA_CODE`를 더 읽지 않는다(테스트로 막았다). 값이 예전 Personal API 키여도 비밀 문자열이라 키로 동작한다. 다만 그 경우 시크릿을 지우거나 바꾸면 기존 캐시를 풀지 못하고 비밀번호 로그인 후 새 키로 다시 저장한다.
> - **라이브러리 확인(작업 1).** garminconnect 0.3.20 소스 기준이다.
>   - `login(디렉터리)`는 `<디렉터리>/garmin_tokens.json`(DI 토큰·리프레시 토큰·client id)을 읽는다.
>   - 만료 15분 전부터는 리프레시해 같은 파일에 다시 쓴다.
>   - 읽기에 실패하면 자격 증명으로 로그인하고 그 파일에 쓴다.
>   - 읽은 토큰이 API에서 거부되면, 자격 증명이 있을 때만 새로 로그인한다.
>   - `tokenstore`를 안 주면 환경 변수 `GARMINTOKENS`를 읽는다(워크플로는 이 이름을 쓰지 않는다).
>   - 웹 전략으로 로그인하면 DI 토큰 없이 파일을 쓸 수 있다. 그때는 저장하지 않고 다음 실행도 비밀번호로 로그인한다(`token_cache=unsaved`).
> - **인증 방식을 정확히 남기는 방법.** 토큰 시도는 자격 증명 없는 클라이언트로 한다. 그래야 토큰이 거부될 때 라이브러리가 조용히 비밀번호로 넘어가지 않고 예외를 낸다. 비밀번호 로그인 전에는 토큰 파일을 지운다. 일시 오류로 첫 시도가 실패했을 때 두 번째 `login`이 같은 토큰으로 성공해 `password`로 잘못 기록되는 것을 막는다.
> - **로그.** garminconnect의 로그인 경고에는 예외 문자열이 실린다(질의 값만 가린다). 그래서 `garminconnect` 로거를 ERROR로 묶었다.
> - **probe(브랜치 `garmin-probe/p4-token-20261125`, 같은 브랜치에 세 번 푸시).** 캐시는 브랜치 범위라서 같은 브랜치에 커밋을 더 푸시해야 앞 실행이 저장한 토큰을 받는다.
>   - 1차(실행 45566808570): 캐시 없음 → `auth=password`, `token_cache=saved`, probe 캐시에 저장. 호출 21건 중 failed 0.
>   - 2차(45566994494): 캐시 복원 → `auth=token`, `token_cache=loaded`, 토큰이 그대로라 저장 생략. 호출 21건 중 failed 0.
>   - probe 결과 파일에 토큰 문자열이 없음을 확인했다.
> - 3차(45567135550, 커밋 메시지 `[probe-bad-key]`): 일부러 틀린 키로 복호화 → `could not be decrypted` 경고 → `auth=password`로 성공, 새 토큰 저장. 호출 21건 중 failed 0.
> - probe가 끝난 뒤 브랜치를 지웠다. probe 캐시(`garmin-tokens-probe-v1-*`)는 7일 동안 쓰이지 않으면 GitHub가 지운다.
> - **S4 2단계(아침 슬롯 추가)는 머지 뒤 `main`에서 `auth=token`이 확인되면 따로 넣는다.**
> - probe 1차 응답 구조(P5용): `get_training_status`는 `mostRecentVO2Max`, `mostRecentTrainingLoadBalance`, `mostRecentTrainingStatus`가 모두 null이다. `get_training_readiness`는 3일 모두 빈 응답이다. 수면은 `dailySleepDTO`의 수면 시간·단계·시각 키가 모두 null이고 `sleepNeed`만 있다. 체성분의 `metabolicAge`는 float인데 10~120 범위 검사에 걸려 버려진다.

선행 조건: 사용자가 `GARMIN_TOKEN_KEY` 시크릿을 등록한다(4장). → 2026-11-25 `GARMIN_TOKENS`에 등록했다(위 진행 기록).

참고: 2026-11-25에 사용자가 `GARMIN_TOKENS`에 넣은 값은 Personal API 키다. 지금 코드는 이 값을 `client.garth.loads`에 넘기다가 `AttributeError`가 나서 비밀번호 로그인으로 넘어가므로, 당장 동작에는 영향이 없다. 하지만 이 키를 garminconnect의 tokenstore로 넘기면 안 된다. 2번에서 `GARMIN_TOKENS` 읽기를 지운다.

작업:

1. **라이브러리 동작 확인.** 고정한 버전의 garminconnect 소스로 다음을 확인한다. 토큰 파일 이름과 위치, 갱신 때 토큰을 파일에 다시 쓰는지, 토큰이 거부되면 자격 증명으로 넘어가는지. `pip download garminconnect==<버전> --no-deps`로 소스를 받아 읽으면 된다.
2. **`build_client` 재작성.** `Garmin(email, password, is_cn=..., prompt_mfa=...)`를 만든 뒤 `client.login(<토큰 디렉터리>)`를 호출한다. garth 경로와 `GARMIN_TOKENS`/`GARMIN_TOKENS_JSON` 읽기는 지운다. 토큰 디렉터리에 garminconnect 형식이 아닌 파일이 있으면 무시하고 비밀번호 로그인으로 넘어간다. 인증 방식은 `::notice::garmin auth=token|password`로 남긴다.
3. **워크플로.**
   - `actions/cache/restore`로 `garmin-tokens-v1-` 접두사의 최신 캐시를 받는다.
   - `openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -pass env:GARMIN_TOKEN_KEY`로 복호화한다. 토큰 디렉터리는 `umask 077`로 만든다. 복호화에 실패하면 파일을 지우고 계속한다(비밀번호 로그인으로 넘어간다).
   - 수집이 끝난 뒤 토큰 파일이 새로 생겼거나 바뀌었으면 암호화해서 `actions/cache/save`로 저장한다. 키는 `garmin-tokens-v1-${{ github.run_id }}`이고, 저장은 `main`에서만 한다.
   - 마지막에 평문 토큰을 지운다(`if: always()`).
4. **probe는 별도 접두사를 쓴다.** `garmin-tokens-probe-v1-`을 쓰고 `main`의 캐시는 복원하지 않는다. refresh 토큰이 갱신 때 바뀌면 `main`에 저장된 토큰이 무효가 될 수 있기 때문이다. probe 브랜치에 두 번 푸시하면 머지 전에 "첫 실행은 password 후 저장, 두 번째는 token" 순환을 검증할 수 있다.
5. **시크릿 검사 스텝.** 대체 경로가 있어야 하므로 `GARMIN_EMAIL`과 `GARMIN_PASSWORD`를 필수로 한다. `GARMIN_TOKEN_KEY`가 없으면 `::warning::`을 남기고 비밀번호 로그인만 한다. 코드는 `GARMIN_MFA_CODE`를 읽지만 워크플로가 넘기지 않으므로 의미가 없다. 지우고, MFA를 켜는 경우의 절차는 README에 적는다(P9).
6. **S4 2단계.** 토큰 인증이 확인되면 아침 슬롯을 2개 더 둔다. 예: 10:41, 12:11 KST.
   - 커밋 수가 하루 2회에서 4회로 늘어난다. 데이터가 그대로면 커밋을 생략할지는 1주 동안 지켜본 뒤 정한다. 생략하면 화면의 "마지막 수집"은 "데이터가 마지막으로 바뀐 수집"을 뜻하게 된다.

완료 기준:

- probe에서 password → token 순환이 확인된다.
- 머지 후 `main`의 연속 두 실행이 각각 `auth=password`(캐시 없음, 저장)와 `auth=token`이다.
- 잘못된 키로 복호화에 실패해도 비밀번호 로그인으로 성공한다(probe에서 확인).
- 로그와 아티팩트에 평문 토큰이 없다.

### P5. 수집 입력 복구(D2, D1, D3)

> 진행: 2026-11-25 `feature/garmin-weight-p5-inputs-20261125`에 구현했다. probe는 날짜를 골라 받는 `--probe-dates`와 값 없이 값의 종류만 남기는 `valueKinds`를 붙여 1회 돌렸다(실행 45571552896, 8일, 호출 56건 중 failed 0). 결과를 읽은 뒤 브랜치를 지웠다.
> - **훈련 부하: 채울 데이터가 없다.** 8일 모두 `get_training_readiness`가 빈 응답이었다. `get_training_status`도 기기별 상태(`latestTrainingStatusData`)가 0개였고 최상위 값이 전부 null이었다. 이 계정에는 준비도·훈련 상태 기록이 없다. 추출기는 계획대로 고쳤다. 준비도 리스트는 그날 항목 중 가장 늦은 것을 쓰고, 훈련 상태는 기기 ID 아래를 깊이 2까지 찾으며 주 기기를 먼저 본다. 계획과 다른 점이 하나 있다. **그날 항목이 없으면 최신 항목을 쓰지 않는다.** 지난 날을 다시 받을 때 오늘 값이 과거 날짜에 들어가기 때문이다. 날짜 키가 아예 없는 응답만 그날 결과로 본다. 준비도에서 값을 얻으면 훈련 상태는 부르지 않는다.
> - **수면: 경로가 맞고, 기록이 적은 것은 착용 때문이다.** 수면이 기록된 6일은 모두 시간·단계·시작/끝 시각 키가 있었다. 시작이 밤 시간대였고, 수면 창이 `enhanced_confirmed_final`이었으며, 단계 합이 총 수면 시간과 같았다(비율 1.0). 즉 낮잠이나 일부 구간이 아니라 짧은 밤잠이 확정 기록된 것이다. 나머지 날은 수면 키가 전부 null이었다. 밤에 기기를 차지 않은 날로 보인다. 추출은 바꾸지 않았다.
> - **대사 나이: 단위 문제였다.** 체성분 응답의 `metabolicAge`는 세가 아니라 "그 나이에 해당하는 생일"의 epoch ms였다. 측정일 기준 나이로 읽으면 3일 모두 10~120세 안이었다. 그래서 10~120 검사에서 늘 버려졌다. epoch ms면 측정일 기준 만 나이로 바꾸도록 고쳤다. backfill하면 체중이 있는 날에 채워진다.
> - **D3.** `exercise_source` 컬럼(`activity`/`intensity`/빈 값)을 CSV 끝에 추가했다. 활동이 있는 날은 활동 값만 쓰고 일일 요약 kcal을 섞지 않는다. **강도 운동 시간은 격렬 2배 가중을 없애고 실제 분(보통+격렬)으로 바꿨다.** 화면 문구 "운동시간"과 맞추고, 활동 시간(실제 분)과 의미를 같게 하려는 것이다. probe 8일 중 기존 행 7일에서 1일의 운동 시간이 바뀌었다(격렬 운동이 있던 날). 칼로리 쪽(일일 활동 칼로리가 운동 칼로리로 들어가는 문제)은 계획대로 P7에서 `exercise_source`를 보고 고친다.
> - **기능 스위치.** `config.json`의 `features`(`sleepMeasurementWeighting`, `loadMeasurementWeighting`, `plateauLoadClassification`)로 켜며 기본은 꺼짐이다. 지금 데이터에서는 수면 점수 54인 체중 측정일(2026-11-19) 하루의 가중치가 빠진다. 현재 EWMA는 84.21→84.20kg, 28일 추세는 주 −0.080→−0.078kg으로 바뀐다.
> - **backfill 준비.**
>   - 수동 실행에 `end_date` 입력을 추가했다.
>   - `backfill_days`는 1~60으로 제한했다. 4일 이상이면 `--protect-existing`이 붙어, 성공했는데 빈 값이 와도 기존 셀을 지우지 않는다. 계획의 "값 손실 0"을 코드로 보장한다.
>   - 모든 실행이 `::notice::garmin merge new_days= filled= changed= cleared= protected=`를 남긴다.
>   - 각 단계 뒤에 봇 커밋의 CSV 차이로도 확인한다.
> - D1 후속(5번)은 P3 판정대로 할 일이 없다.

### P6. 진단 정합성(섀도 감사 수정·유지)

작업:

3. **강건 회귀.** `robust_regression_56d`를 실제 강건 추정(Theil–Sen 또는 MAD 기준 이상치 제거)으로 바꾼다.
4. **중복 제거.** `flat_baseline`과 `ewma_baseline`이 같은 계산이다. 둘을 구분하거나 하나를 지운다. Kalman 백테스트는 한 번만 돌리고 결과를 함께 쓴다.
5. **같은 표본.** 기준 시점 집합 하나와 실측 매칭 함수 하나를 모든 모델(운영, 후보, Kalman, 변화 없음)에 적용한다. 최소 표본 기준도 통일한다. Kalman이 증량 속도를 0으로 자르는 점(`kalman_predictor.py:136`)은 운영 모델과 맞추거나, 차이를 진단에 명시한다.
6. **선택 게이트.** 계획서(`.kilo/plans/garmin-weight-model-hardening.md`)의 수용 기준을 구현한다.
   - bias가 나빠지면 채택하지 않는다.
   - 여러 예측 기간에서 이겨야 한다.
   - 같은 표본으로 비교한다.
   - 상태 값은 섀도에 맞게 `shadow_leader`/`no_change`로 둔다. 운영 예측에 연결되지 않은 모델에 `adopted`를 쓰지 않는다.
   - 운영 모델을 실제로 바꾸는 일은 이번 범위 밖이다. 섀도 우세가 몇 주 이어지면 따로 정한다.
7. **M3.** 백테스트는 감량기만이 아니라 모든 기준 시점에서 평가한다. 화면의 "14D MAE"는 전체 표본 값을 쓴다. 예측 기간에 **84일**을 추가한다. 화면이 3개월 예측을 보여 주는데 지금은 그 기간을 아무도 평가하지 않는다(1장 M8 근거 참고).
8. **M4.** 신뢰구간 적중률은 기준 시점마다 그 시점의 감량률과 구간 폭으로 다시 계산한다. 증량·유지 추세에서도 값이 나와야 한다.
9. **M9.** `model_audit.py`가 운영 코드의 함수를 그대로 불러 쓰게 해서 공식이 둘로 갈리지 않게 한다. `ciHitRateApprox`는 재현값으로 바꾼다.
10. **M1(최종).** 진단 패널을 표 하나로 합친다. 운영 / 섀도 후보 / Kalman / 변화 없음을 같은 표본 수(n)와 함께 보여 주고, 서로 모순되는 줄이 없게 한다.

필수 테스트:

- 정확히 선형인 시계열에서 회귀 후보의 MAE가 0.01kg 미만이다. 부호 회귀를 막는다.
- 평탄 구간에 이상치 한 점을 넣어도 강건 회귀의 기울기가 일반 회귀보다 덜 움직인다.
- 모든 모델의 표본 집합이 같다.
- bias가 나빠지는 후보는 게이트를 통과하지 못한다.
- 포함률을 알고 만든 합성 시계열에서 신뢰구간 적중률이 그 포함률로 재현된다.

완료 기준. 리포트가 별도로 재현한 값을 검증 기준으로 쓴다.

- 운영 모델의 전체 표본 MAE가 약 0.524/0.558/0.673kg(n=223/216/202)이다.
- 신뢰구간 적중률이 약 81%/83%/88%다.
- 부호를 고친 56일 회귀가 약 0.522/0.571/0.701kg이다.
- 258행 생성 시간은 1초 미만(현재 0.20초), 1,095행은 5초 미만이다.

### P7. 예측 곡선 정합성(감쇠 곡선 유지)

작업:

1. **M5, 감쇠율 상한.** 지금은 `k = min(rate/gap, 2·ln2/16 ≈ 0.087/주)`(`sync_modeling.py:383-385`)다. 목표가 가까우면 상한에 걸려 초기 기울기가 실제 추세보다 훨씬 완만해지고, 세 시나리오가 같은 k를 갖게 된다. 후보는 두 가지다.
   - (a) 상한을 없애고 `k = rate/gap`으로 둔다. 초기 기울기가 추세와 같아진다. 간격이 아주 작을 때만 보호한다.
   - (b) 간격이 일정 범위로 줄어들 때까지는 선형으로 가다가 그 뒤 감쇠한다.

   P6의 같은 표본 백테스트(7/14/28/84일)에서 MAE가 나빠지지 않는 쪽을 고른다. 84일에서는 평평한 예측도 비교 대상에 넣는다. 시나리오마다 각자의 k를 쓴다.

   (a)를 고르면 초기 2주처럼 감량률이 높게 나올 때(수분·글리코겐 손실) 곡선이 목표로 빠르게 붙는다. 이 경우를 따로 확인한다. P1의 `cold_start_flat` 구간은 감량률 0이라 영향이 없다.
2. **ETA.** 곡선이 `목표 + ε` 이하로 처음 내려가는 날로 정한다. ε의 기본값은 0.3kg이고 `config.json`의 `etaToleranceKg`로 바꿀 수 있다. 일별 실측과 추세의 평균 차이가 0.44kg이므로, 그보다 작은 차이는 실측으로 구분되지 않는다. 12주 밖도 최대 104주까지 계산하고, 그래도 닿지 않으면 "2년 이후"로 표시한다. ETA 범위는 시나리오 곡선들에서 구한다.
3. **추세 지연, M9 결측 보정.** 시간 간격을 반영하는 EWMA로 바꾼다(간격 Δt에 따라 α를 정한다). 리포트의 합성 예(주 0.4kg 감량, +0.52kg 지연)에서 지연이 줄어드는지 확인한다. 백테스트가 나빠지지 않을 때만 채택한다.
4. **M6.** 백엔드가 시나리오별 예측 시계열(13점 × 3)과 구간을 `scenarios[].series`로 내보낸다. 프런트엔드는 그대로 그리고, 비율로 늘리는 로직(`app.helpers.js:89-114`)은 지운다. 대시보드가 읽는 `predictions.*`, `predictionCI.series`, `series.prediction`은 기준 시나리오 값으로 유지한다.
5. **F3.** 날짜를 숫자(일 단위)로 넘기는 선형 x축을 쓴다. 눈금 문자열은 콜백으로 만든다. 어댑터 라이브러리는 추가하지 않는다.
6. **F6(선).** 시나리오 카드마다 자기 시계열로 스파크라인을 그린다.
7. **M7, 인사이트.**
   - `durationDays`는 실제로 연속된 정체 길이로 계산한다.
   - 문구를 상태별로 나눈다: 감량 중 / 감량 후 정체 / 감량 없이 정체 / 증량.
   - "대사 적응"은 직전에 실제 감량이 있었을 때만 쓴다.
   - 증량 상태에 맞는 문구를 새로 만든다.
   - 출처가 불분명한 "CDC/WHO 기준" 표기는 중립적인 문구로 바꾼다.
   - F7의 시나리오 흐림 안내도 바뀐 계산에 맞춘다.
8. **M9 나머지.**
   - 세션 kcal 가정(주 4회 고정)은 P5의 `exercise_source`를 반영해 고친다.
   - kcal/kg 구간 경계에 이력 현상(hysteresis)을 넣는다. 예: 30% ± 0.5%.
9. **D2 기능 판정.** P5 이후 데이터가 있는 구간에서 정체 유형 분류, 부하 가중치, 수면 가중치를 켰을 때와 껐을 때를 백테스트로 비교한다. 나빠지지 않는 기능만 켠다. 데이터가 모자라 판정할 수 없으면 꺼 둔 채 다음 점검 날짜를 적는다.

완료 기준. 리포트 M5의 합성 예(주 0.4kg, 90일, 목표 80kg)에서 다음이 나와야 한다.

- 곡선의 초기 기울기가 주 0.40kg ± 5%다(지금은 0.12kg).
- ETA 날짜의 곡선 값이 `목표 + ε` 이하다.
- 세 시나리오 카드의 값이 서로 다르다.
- 카드의 값과 차트 선의 끝 값이 0.01kg 안에서 같다.
- 60일 보기에서 과거와 미래의 하루당 픽셀 수가 같다.

## 7. Garmin Personal API 검토 결과(보류)

2026-11-25에 검토했다. 사용자는 기존 방식(garminconnect) 유지를 골랐다. 비밀번호 로그인이 막혔을 때의 대체 수단으로 기록해 둔다.

출처:

- https://developer.garmin.com/gc-developer-program/personal/personal-api/
- https://developer.garmin.com/gc-developer-program/personal/personal-faq/
- Swagger 페이지 번들에 내장된 명세
- Garmin의 참조 구현 https://github.com/garmin/connect-personal-api-python (Apache-2.0, PyPI `garmin-connect-personal-api-python` 1.1.0, 2026-10 공개)

| 항목 | 내용 |
|---|---|
| 대상 | 자기 Garmin Connect 데이터를 읽는 개인용이다. 여러 사용자를 상대하는 상업용은 대상이 아니다. 키를 만들 때 약관에 동의한다. 별도 승인 절차는 문서에 없다. |
| 키 | `https://connect.garmin.com/app/settings/personalApiToken`에서 만든다. 만료 기간은 30/90/180일 또는 1년 중에서 고른다. 만료 약 1주 전에 메일이 온다. 키는 만들 때 한 번만 보여 준다. 삭제하면 그 키로 발급한 토큰도 모두 무효가 된다. |
| 토큰 | `POST https://personal.connectapi.garmin.com/personalapitoken-service/personal-api/personal-api-key/token`에 `Authorization: ApiKey <키>`를 보내면 응답 본문으로 JWT가 온다. 24시간 유효하고 refresh 토큰은 없다. 실행마다 새로 교환하면 되므로 저장할 상태가 없다. 데이터 요청에는 `Authorization: Bearer <JWT>`를 쓴다. |
| 데이터 경로 | Swagger에 28개가 있다. 체중·체성분은 `/weight-service/weight/range/{start}/{end}?includeAll=true`다(스키마에 `bodyFat`, `visceralFat`, `metabolicAge`, `bmi`, `muscleMass`가 있다). 일일 요약은 `/usersummary-service/v2/dailysummaries?startDate=&endDate=`다(`totalSteps`, `restingHeartRate`, 중·고강도 운동 시간, `activeKilocalories`). 수면은 `/sleep-service/sleep/dailySleepSummariesByDate`다(`sleepTimeSeconds`, `sleepScores`). 활동은 `/activitylist-service/activities/search/activities?startDate=&endDate=`다. 그 밖에 HRV, 바디 배터리, 스트레스, VO2max, 심박 구간이 있다. |
| 없는 것 | 훈련 준비도, 훈련 상태, 급성 훈련 부하. 명세에 경로도 필드도 없다. |
| 문서에 없는 것 | 속도 제한, 오류 코드 규칙, 서버·CI에서 써도 되는지, 체중계로 잰 뒤 데이터가 반영되기까지의 지연, 공개 웹에 게시하는 것에 관한 조건(일반 약관은 읽지 않았다). |
| 전환할 때 얻는 것 | 비밀번호·SSO·MFA 위험이 사라진다. 토큰 캐시와 암호화가 필요 없다. 공식 경로다. 기간 단위 요청이라 호출이 실행당 5회 안팎으로 줄어든다. 의존성이 `httpx` 하나로 준다. |
| 전환할 때 할 일 | 새 클라이언트를 probe에서 dry-run으로 며칠 돌려, 겹치는 날짜의 값(체중, 체지방, 걸음 수, 안정 심박)이 기존 CSV와 같은지 대조한 뒤 전환한다. 단위(그램 등)와 필드 차이를 이때 맞춘다. |
