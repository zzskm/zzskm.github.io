# garmin-weight 점검 리포트

2026-11-25 점검. 기준은 `main`의 `8a54bf36be`(체중 데이터 최신 커밋 `e1478a2d51`)다. **이번 세션은 점검과 이 문서 작성까지만 했고 코드·데이터는 수정하지 않았다.** 개선 작업은 다음 세션에서 이 문서를 기준으로 진행한다.

경로는 따로 적지 않으면 `garmin-weight/` 기준이고, 줄 번호는 위 커밋 기준이다.

## 1. 요약

동기화는 매일 돌고 있고, CSV 이력 428커밋을 전수 대조한 결과 값이 사라진 적은 한 번도 없다. 요약 생성도 결정적이며 성능 여유가 크다. 문제는 네 갈래다.

1. **화면이 지금 틀린 정보를 보여 준다.** "예측 보류" 배너가 조건과 무관하게 항상 떠 있고, 모델명은 실제로 쓰지 않는 `ma7_baseline`으로 표시되며, 인사이트는 항상 "13일째 정체"라고 말한다. 차트 범례에는 내부 라벨(`ciUpper`/`ciLower`)이 노출되고 범례에 있는 목표선은 그려지지 않는다.
2. **동기화가 조용히 망가질 수 있는 구조다.** 토큰 재사용 경로는 처음부터 동작하지 않아 매 실행 비밀번호로 로그인하고 있다. 로그인 이후의 API 실패는 전부 삼켜져, 아무것도 못 가져와도 성공으로 끝나고 "동기화 시각"만 갱신된다. 예약 실행은 크론 시각보다 중앙값 약 6시간 늦게 반영된다.
3. **모델 진단부에 계산 오류가 있다.** 섀도 감사의 회귀 후보는 부호가 뒤집혀 오차가 2배로 계산되고, 모델 비교는 서로 다른 표본끼리 이루어진다. 그 결과가 위 1번의 잘못된 모델명 표시로 이어진다.
4. **테스트가 CI에서 한 번도 실행되지 않는다.** 그 사이 테스트 1건이 2026-08-12 커밋 이후 계속 실패 중이다.

확인하지 못한 것은 다음과 같다.

- **Actions 실행 로그와 실행 이력.** 조회하지 않았고 커밋 시각으로 대신했다. 실패한 실행은 커밋을 남기지 않으므로 실패 횟수는 알 수 없다.
- **실제 Garmin API 응답.** 자격 증명이 없어 응답 형태는 라이브러리 소스로만 판단했다.
- **iOS 실기기 동작**(홈 화면 아이콘, 설치)과 스크린리더 실사용.

검증에 쓴 임시 스크립트는 세션 임시 폴더에 있고 저장소에는 넣지 않았다. 각 항목에 재현 방법을 적었다.

## 3. 동기화·운영

### S1. 토큰 재사용 경로가 동작하지 않아 매 실행 비밀번호로 로그인한다 — 높음, 코드 확인

`scripts/sync_garmin.py:233-240`은 `client.garth.loads(token)`으로 토큰을 복원한다. 그런데 `requirements.txt:5`가 `garminconnect>=0.3.2`라서 러너에는 최신인 0.3.20이 설치되고, 0.3.x는 garth를 버리고 자체 클라이언트(`client.client`)로 바뀌었다. `Garmin` 객체에 `garth` 속성이 없으므로 `AttributeError`가 나고, 광범위한 `except`가 이를 잡아 비밀번호 로그인으로 넘어간다.

- 0.3.20 휠 전체에서 `garth` 문자열은 구형 토큰을 거부하는 코드(`_is_legacy_garth_tokenstore`)에만 나온다. 라이브러리는 구형 토큰을 "no longer supported"로 처리한다.
- 커밋 `1f7b3190a2`(2026-04-24, "handle missing garth attr")가 로그인 뒤의 `garth.dumps()`만 우회했으므로, 이 경로는 스크립트가 만들어진 날부터 죽어 있었다.
- `sync_garmin.py:236`의 `client.username`은 생성자에 넘긴 이메일을 돌려주는 단순 속성이라 토큰을 검증하지 않는다.
- 데이터가 매일 들어오고 있으므로 `GARMIN_EMAIL`/`GARMIN_PASSWORD`로 하루 2회 SSO 로그인이 일어나고 있다고 봐야 한다. 실행 로그에 `token reuse failed` 경고가 매번 찍히는지 보면 확정된다.

영향: 데이터센터 IP에서 반복되는 비밀번호 로그인은 429 차단, 계정 잠금, MFA 요구에 취약하다. 지금 저장된 `GARMIN_TOKENS` 시크릿은 쓸 수 없는 형식이다. `GARMIN_MFA_CODE`는 코드가 읽지만(`sync_garmin.py:250`) 워크플로가 넘기지 않는다.

개선 방향:

- 0.3.x 방식으로 바꾼다. `Garmin(email, password, prompt_mfa=...)`를 만든 뒤 `client.login(tokenstore)`를 호출하면, 토큰이 유효할 때는 토큰으로, 없거나 거부되면 자격 증명으로 로그인한다. `tokenstore`는 경로 또는 JSON 문자열이고 환경 변수 `GARMINTOKENS`도 읽는다.
- 토큰은 `di_token`/`di_refresh_token`/`di_client_id`이며 갱신 때 refresh 토큰이 바뀔 수 있다. 경로로 넘기면 라이브러리가 갱신분을 파일에 다시 쓴다. 따라서 실행 간에 토큰 파일을 보존해야 한다.
- 보존 방법은 결정이 필요하다(9장). 공개 저장소의 Actions 캐시는 포크 PR 워크플로가 읽을 수 있으므로 평문으로 넣으면 안 된다.
- 인증을 바꾼 뒤에는 `workflow_dispatch`로 러너에서 직접 확인한다. 로컬 성공만으로는 부족하다.

### S2. 로그인 이후의 호출 실패가 전부 묻히고 성공으로 끝난다 — 높음, 재현됨

`safe_call`(`sync_garmin.py:213-222`)은 모든 예외를 경고 로그만 남기고 기본값으로 바꾼다. 하루치 호출이 전부 실패하면 `_row_is_empty`(`:916-919`)가 참이 되어 기존 행을 유지하고, 스크립트는 0으로 끝난다. 이어서 `generatedAt`(`:856`)이 새로 찍힌 요약이 커밋된다.

- 재현: 모든 메서드가 예외를 던지는 가짜 클라이언트로 `fetch_day_row`를 호출하면 예외 없이 빈 행이 나오고 `_row_is_empty`가 `True`다.
- 화면의 "동기화 11. 25. 오전 08:49"는 Garmin에서 받아 온 시각이 아니라 요약 파일을 만든 시각이다. API가 며칠 막혀도 이 시각은 계속 새로워진다.
- 워크플로의 "Rebuild summary from CSV" 스텝(`garmin_weight_sync.yml:78-80`)도 가져오기 없이 `generatedAt`을 갱신한다.

개선 방향: 실행별 수집 결과(성공·실패 호출 수, 마지막 수집 성공 시각)를 `summary.json`에 넣고 화면의 동기화 표시를 그 값으로 바꾼다. 요청한 날짜가 전부 빈 행이면 작업을 실패 처리하거나 `::warning::`을 남긴다. `safe_call`이 "실패"와 "데이터 없음"을 구분해 돌려주게 한다.

### S3. 일부 호출만 실패하면 기존 값이 빈 값으로 덮인다 — 중간, 재현됨(이력상 발생 0건)

행 보호는 핵심 필드가 **전부** 비었을 때만 작동한다(`sync_garmin.py:932-935`). 체성분 호출만 실패하고 걸음 수는 성공하면 새 행의 체중이 `None`인 채로 기존 행을 통째로 교체한다.

- 재현: 체성분 호출만 예외를 던지는 가짜 클라이언트로 2026-11-24를 다시 받으면 체중 84.1, 체지방 29.3이 `None`이 되고 `_row_is_empty`는 `False`다.
- 날짜마다 3일 × 하루 2회 = 6번 덮어쓰이므로 대부분 다음 실행이 복구한다. 그 날짜를 마지막으로 다루는 실행에서 실패하면 영구 손실이다.
- CSV 이력 428커밋을 전수 대조했고 값이 있다가 빈 값이 된 경우는 0건이다. 아직 일어나지 않은 잠재 위험이다.

개선 방향: 필드 단위로 병합한다. 해당 호출이 실패했으면 기존 값을 유지하고, 호출이 성공했는데 값이 없을 때만 비운다(S2의 실패 구분이 선행되어야 한다).

- 2026-11-06에 아침 실행을 09:00 KST로 옮겼지만(`c6492520e4`), 그 뒤 36회 실행의 지연은 최소 125분, 중앙값 361분, 최대 529분이다. 09시 슬롯은 실제로 13:50~17:46 KST에, 자정 슬롯은 04:18~08:49 KST에 반영됐다(11:05 1회).
- 아침에 잰 체중이 오후 2~3시에야 화면에 나타나는 날이 많다는 뜻이다.
- 430개 슬롯 중 다음 슬롯 전까지 커밋이 없던 것은 9개다. 실행 누락인지 지연인지는 커밋만으로 구분되지 않는다.
- 9월부터 악화된 원인은 확인하지 못했다. 버스 수집 워크플로(`bus_arrival.yml`)가 2026-09-17에 추가된 시기와 겹친다는 정황뿐이고 인과는 검증하지 않았다. Actions 탭에서 예정 시각과 시작 시각의 차이를 보면 구분된다.

개선 방향: 두 크론이 모두 정각(`0 15`, `0 0`)인데, 정각은 GitHub 예약 실행이 가장 밀리는 시간대다. 분을 정각에서 벗어나게 옮기고, 아침 시간대에 슬롯을 두세 개 두어 지연을 흡수하는 방법이 있다. 슬롯을 늘리기 전에 S6의 체크아웃 부담을 먼저 줄인다. 시각 보장이 꼭 필요하면 외부에서 `workflow_dispatch`를 호출하는 방식이 남는다.

### S5. 핵심 의존성이 고정되지 않았고 쓰지 않는 패키지를 설치한다 — 중간, 코드 확인

- `requirements.txt:5-6`의 `garminconnect>=0.3.2`, `garth>=0.5`만 범위 지정이고 나머지는 정확히 고정돼 있다. 0.3.2 이후 6개월여 동안 17번 릴리스됐고(최신 0.3.20, 2026-10-23) 매 실행 최신이 설치된다. S2 때문에 호환이 깨져도 조용히 0으로 채워진다.
- garminconnect 0.3.x는 garth를 요구하지 않는다. `garth>=0.5`는 garth 0.8.0과 그 의존성(logfire, pydantic, pydantic-settings, requests-oauthlib)을 쓸모없이 설치한다.

개선 방향: `garminconnect`를 정확한 버전으로 고정하고 `garth`를 제거한다. 버전 올림은 의도적으로 하고 러너에서 확인한다.

## 5. 예측 모델·진단

먼저 문제가 없다고 확인한 것을 적는다.

- 같은 기준 시점끼리 비교하면 운영 모델은 "변화 없음" 기준선보다 낫다. 7/14/28일 MAE가 0.524/0.558/0.673kg 대 0.548/0.617/0.753kg이다(표본 223/216/202).
- 80% 예측 구간을 시점마다 다시 만들어 대조하면 실제 포함률은 81%/83%/88%다. 구간 폭은 타당하다.
- 일별 체중과 추세의 차이는 평균 0.44kg이다. 어떤 예측도 하루치 실측과 비교하면 이 아래로 내려가기 어렵다는 뜻이다.

### M1. 채택하지 않은 모델을 채택했다고 표시한다 — 높음, 재현됨

현재 `summary.json`의 `modelDiagnostics.selectedModel`은 `{"name": "ma7_baseline", "status": "adopted_new"}`이고 화면에 "MEDIUM · 3점 · ma7_baseline"으로 나온다(`app.js:205-206`). 그러나 `selectedModel`은 `sync_garmin.py:838`에서 진단 정보로만 들어갈 뿐 예측 계산에 쓰이지 않는다. 예측은 여전히 다중 윈도우 EWMA 혼합이다.

판정 자체도 무효다. 비교 대상의 표본이 서로 다르다. 운영 모델 백테스트는 감량 추세였던 시점만 평가하고(95개, `sync_modeling.py:568-570`), `ma7_baseline`은 기준일에 측정이 있던 시점만 평가한다(134/129/117개). 표본 수 기준도 운영 모델은 3개, 후보는 20개다. 바로 아래 "모델 검증" 줄은 Kalman과만 비교해 "우세 current"라고 써서 같은 패널 안에서 서로 모순된다.

계획서(`.kilo/plans/garmin-weight-model-hardening.md`)의 수용 기준 중 "bias가 나빠지면 채택하지 않는다"와 "운영 모델과 같은 로직·같은 실측 매칭으로 비교한다"는 구현되지 않았다.

### M2. 섀도 감사의 회귀 후보는 부호가 뒤집혀 있다 — 높음, 재현됨

`compute_candidate_prediction`은 `weekly_change = -slope * 7`, 즉 감량이 양수인 값을 돌려주는데(`sync_modeling.py:1022` 등), `run_generalized_backtest`는 이를 더한다(`:1107-1108`). 감량 추세에서 체중이 늘어난다고 예측한다.

- 재현: 하루 0.05kg씩 정확히 줄어드는 120일 시계열에서 `linear_regression_28d`의 MAE는 0.7/1.4/2.8kg으로, "변화 없음" 기준선(0.35/0.7/1.4kg)의 정확히 2배다. 올바른 회귀라면 0에 가까워야 한다.
- 실제 데이터에서 부호를 바로잡으면 56일 회귀의 MAE는 0.605/0.782/1.124kg에서 0.522/0.571/0.701kg으로 내려가 운영 모델과 같은 수준이 된다. 지금 `modelAudit`에 실린 회귀 후보 수치는 모두 틀렸다.

같은 함수의 다른 문제:

- `robust_regression_56d`는 이상치를 걸러내지 않고 1% 키운다(`:971-973`). 84.0kg 평탄 구간에 87.0kg 한 점을 넣으면 일반 회귀는 주당 +0.018kg, 이쪽은 +0.029kg이 나온다.
- `flat_baseline`과 `ewma_baseline`은 같은 계산이다(`:994-999`, `:1009-1014`).
- Kalman 백테스트가 `build_summary`와 `run_generalized_backtest` 양쪽에서 한 번씩 실행된다.

### M3. 표시되는 백테스트 오차가 현재 상태를 대표하지 않는다 — 중간, 재현됨

`backtest_predictions`는 감량률이 양수인 시점만 평가한다(`sync_modeling.py:568-570`). 지금 모델은 증량·유지 추세에서도 예측선을 그리는데(2026-08-12 변경), 화면의 "±0.61 kg (14D MAE)"는 감량기 95개 시점에서만 나온 값이다. 전체 시점으로 계산하면 0.558kg이다. Kalman 비교(`modelComparison`)도 Kalman은 전체 시점(223/216/202개), 운영 모델은 95개로 표본이 다르다. Kalman 쪽은 증량 속도를 0으로 자르는 점도 다르다(`kalman_predictor.py:136`).

### M4. 신뢰구간 적중률이 감량 추세가 아닐 때는 항상 비어 있다 — 중간, 재현됨

`central_fn`은 현재 감량률이 0 이하이면 `None`을 돌려준다(`sync_garmin.py:800-803`). 그래서 지금 `ciCalibration.hitRate`는 전부 `null`이고 화면에는 "검증 대기"가 나온다. 감량 추세일 때도 과거 모든 시점에 **오늘의** 감량률과 **오늘의** 구간 폭을 적용하므로 재현이 아니다. 시점별로 다시 계산한 실제 포함률은 위에 적은 81%/83%/88%다.

### M5. ETA와 예측 곡선이 서로 다른 모델이다 — 중간, 재현됨

ETA는 선형이고(`sync_garmin.py:683`), 예측선은 목표 체중으로 수렴하는 지수 감쇠다(`sync_modeling.py:360-388`). 지수 감쇠는 목표에 닿지 않는다.

- 재현: 주당 0.4kg씩 꾸준히 빠지는 90일 시계열, 목표 80kg. ETA는 26일인데 그 날짜의 곡선 값은 81.04kg이고 12주 끝도 80.51kg이다.
- 감쇠율 상한(`:383-385`) 때문에 목표가 가까우면 곡선의 초기 기울기가 실제 추세(주 0.40kg)보다 훨씬 완만해지고(약 0.12kg), 세 시나리오가 같은 곡선이 된다. 위 예에서 시나리오 카드는 셋 다 80.51kg이다.
- 추세 체중은 실제보다 뒤처진다. 위 예에서 +0.52kg, 주당 0.2kg이면 +0.25kg이다. 남은 체중과 ETA가 그만큼 크게 나온다.

곡선의 수렴점이 사용자가 설정한 목표라서 `targetWeightKg`를 바꾸면 예측과 백테스트 수치가 함께 바뀐다는 점도 기록해 둔다.

### M6. 시나리오 카드의 숫자와 차트의 선이 다른 계산이다 — 중간, 재현됨

카드의 3개월 체중은 백엔드가 시나리오별 감량률로 계산하고, 차트 선은 프런트엔드가 기준 예측선을 감량률 비율로 늘려 만든다(`app.helpers.js:89-114`). 지수 감쇠 구간에서는 둘이 다르다.

| 시나리오 | 현재 데이터: 카드 / 선 끝 | M5의 합성 예: 카드 / 선 끝 |
|---|---|---|
| 낙관 | 83.27 / 83.19 | 80.51 / 80.05 |
| 기준 | 84.69 / 84.69 | 80.51 / 80.51 |
| 보수 | 86.18 / 86.19 | 80.51 / 80.97 |

기준 감량률이 0에 가까우면 비율이 폭주하고, 정확히 0이면 세 선이 같아진다. 지금 기준 감량률은 −0.0397로 0에 가깝다.

개선 방향: 백엔드가 시나리오별 예측 시계열(13점 × 3)을 내보내고 프런트엔드는 그대로 그린다.

### M7. 인사이트 문구가 사실과 다르다 — 중간, 재현됨

현재 문구는 "13일째 정체 중이지만 대사 적응 과정의 정상 패턴입니다. 운동량 10% ↑ 또는 식단 변화로 돌파해 보세요."다.

- `durationDays`는 고정 창의 양 끝 날짜 차이라서 항상 13이다(`sync_modeling.py:690-694`). 전체 이력에서 정체가 감지된 21일 모두 13이 나왔다.
- 현재 체중 84.1kg은 기록 시작 체중 84.2kg과 같고 28일 추세는 주당 +0.08kg이다. 감량이 없던 상태에 "대사 적응"을 말한다(`:736-741`). 정체 유형과도 무관하게 같은 문구다.
- 증량·유지 추세에서는 `lossIntensity`가 `None`이라 안내가 아예 없다. 목표에서 멀어지는 상황에 대한 문구가 없다.

### M8. 이력이 짧을 때 예측이 평평한 값으로 나온다 — 낮음, 재현됨

10일치 데이터면 감량률은 `None`인데 1개월·3개월 예측은 현재 값 그대로(81.55) 나오고, 추세는 "감량 중 0.32kg/주", 신뢰도는 "보통"이다. T1의 실패 테스트가 기대하던 "이력이 짧으면 예측을 내지 않는다"와 어긋난다. 2026-08-12 변경("숨기지 않고 신뢰도를 표시")의 부수 효과로 보이며, 어느 쪽이 맞는지 결정이 필요하다.

### W1. Chart.js CDN이 실패하면 빈 화면에서 멈춘다 — 높음, 재현됨

### W2. 서비스 워커 데이터 캐시가 계속 쌓이고 오프라인에서 가장 오래된 데이터를 준다 — 중간, 재현됨

앱은 `summary.json?ts=…`로 요청하고 `networkFirst`는 그 URL 그대로 저장한다(`sw.js:74`). 로드할 때마다 요약(약 96KB)과 설정이 새 항목으로 쌓이고, `CACHE_VERSION`을 바꾸기 전에는 지워지지 않는다. 5회 로드 후 데이터 캐시 항목은 8개였다.

오프라인 대체는 `ignoreSearch`로 찾는데(`:77`) 처음 저장된 항목이 돌아온다. `generatedAt`을 달리한 세 버전을 차례로 캐시한 뒤 네트워크를 끊으면 가장 최근(2030-03-03)이 아니라 가장 오래된 것(2030-01-01)이 나왔다.

개선 방향: 저장할 때 쿼리를 뗀 URL을 키로 쓴다. 증가와 순서 문제가 함께 해결된다.

### W3. CDN 자산은 서비스 워커 캐시에 들어가지 않는다 — 중간, 재현됨

Chart.js와 CDN 스타일시트는 `crossorigin` 없이 불러와 응답이 불투명하고, `res.ok`가 거짓이라 저장되지 않는다(`sw.js:98`). 5회 로드 후 런타임 캐시에는 글꼴 파일 2개뿐이었다. 오프라인에서 차트가 나오는 것은 브라우저 HTTP 캐시 덕분이고(확인함), 그 캐시가 비면 W1의 빈 화면이 된다. Chart.js에 `integrity`도 없다(`index.html:346`).

개선 방향: `integrity`와 `crossorigin="anonymous"`를 붙이면 무결성 검증과 캐시 저장이 함께 해결된다. 또는 Chart.js를 저장소에 넣는다.

## 8. 그 밖의 사항 — 낮음

- **공개 범위.** 저장소와 Pages가 공개라서 일별 체중, 체지방률, 안정 심박, 걸음 수가 누구에게나 보이고 git 이력에 남는다. 루트 `index.html`의 목록에 `garmin-weight`가 있고 `noindex`나 `robots.txt`는 없다. 의도한 공개라면 조치가 필요 없다. 검색 노출만 줄이려면 `noindex` 메타 한 줄이다.
- **요약 파일의 군살.** 약 96KB이고 들여쓰기를 빼면 52KB다. 두 소비자 어느 쪽도 읽지 않는 부분은 `series.ma7`(약 14KB), `series.steps`, `series.exerciseMinutes`, `series.predictionCI`(`predictionCI.series`와 중복), `modelDiagnostics.modelAudit`(약 3.9KB)이다. 일별 시계열 4개가 전체 이력을 담아 하루 약 220바이트씩 늘어난다.

## 9. 결정이 필요한 사항

다음 세션이 시작하기 전에 정해 두면 작업이 갈리지 않는다.

1. **토큰 보관 방식(S1).** 암호화한 토큰 파일을 Actions 캐시에 두는 방법, 세분화된 PAT로 시크릿을 갱신하는 방법, 비밀번호 로그인을 유지하고 실패 감지만 강화하는 방법 중 하나.
2. **섀도 감사를 고칠지 뺄지(M1~M4).** 후보 모델 비교·선택 게이트·Kalman은 설계상 "섀도"인데 지금은 틀린 표시만 만든다. 고쳐서 유지하거나, 운영 요약에서 빼고 `model_audit.py` 같은 오프라인 도구로만 남길 수 있다. 운영 모델이 단순 회귀와 같은 수준이라는 점도 판단 근거다.
3. **이력이 짧거나 추세가 없을 때의 예측 표시(M8).** 숨길지, 표시하되 신뢰도를 낮출지.
4. **수면·훈련 부하·대사 나이 입력(D2).** 추출을 고쳐서 살릴지, 컬럼과 관련 기능을 뺄지.
5. **활동 데이터(D1).** Garmin Connect에서 5월 15일 이후 활동 기록 유무를 확인해 준다.
6. **ETA와 예측 곡선(M5).** 선형으로 통일할지, 감쇠 모델을 유지하고 ETA를 그 곡선에서 구할지.

## 10. 권장 작업 순서

묶음 사이의 의존은 "2는 1과 무관, 4는 3이 있으면 안전" 정도다.

1. **화면의 오표시 제거(작고 안전함).** F1, F2(기본 범례 끄기·목표선·범례 색), F4, F5, F6, F7의 "N일 전"·칩 기본값, A2, 모바일 푸터. 대부분 몇 줄짜리다. M1은 우선 모델명 표시만 떼어도 된다.
2. **동기화 신뢰성.** S5(버전 고정, garth 제거) → S1(인증 교체) → S2(실패 가시화) → S3(필드 병합). 러너에서 확인한다. S4의 크론 조정과 S6의 얕은 체크아웃을 같이 한다.
3. **테스트 CI.** T1의 워크플로 추가와 실패 테스트 정리, T2의 무력한 단언 수정. 이후 묶음의 안전망이다.
4. **모델 정합성.** D4(오늘 행 분리), M2(부호), M3·M4(같은 표본·시점별 재현), M5·M6(ETA와 시나리오 시계열), M7(인사이트). 9장의 2·3·6번 결정이 먼저다.
5. **PWA·로딩.** W1(대기 제한), W2(캐시 키), W3(`integrity`/`crossorigin`), W4(글꼴), W5(아이콘).
6. **정리.** 죽은 코드, 요약 군살, A1(대비)·A3, README.

## 11. 작업할 때 지켜야 할 것

- **`summary.json`의 소비자는 둘이다.** 체중 페이지 외에 개인 대시보드(`dashboard.js`, `dashboard-model.js`)가 다음을 읽는다: `generatedAt`, `current.{weightKg, weightDate, bodyFatPercent}`, `rolling.{last7StepsAvg, last7ExerciseMinutes, lossRateDetail.blended, exerciseTrend.deltaPct}`, `predictions.{oneMonthWeightKg, threeMonthWeightKg}`, `modelDiagnostics.confidence`, `modelDiagnostics.trend.{predictionEnabled, disabledReason}`, `predictionCI.series`, `series.{daily, ewma, prediction}`. 스키마를 바꾸면 `tests/test_dashboard_browser.py`의 픽스처(`:60-75`)도 함께 본다.
- **데이터 파일은 봇이 하루 2회 `main`에 커밋한다.** 작업 브랜치에서는 `data/daily_metrics.csv`와 `data/summary.json`을 커밋에 넣지 않는다. 요약을 다시 만들어 볼 때는 `--output-summary`로 다른 경로를 준다.
- **긴 backfill은 D1을 확인한 뒤에만 한다.**
- **로컬 환경.** pytest와 garminconnect가 설치돼 있지 않다. 단위 테스트는 저장소 루트에서 `PYTHONUTF8=1 python -m unittest tests.test_garmin_weight`로 돌린다. Playwright는 시스템 Chrome으로 동작한다. 서비스 워커를 확인하려면 `garmin-weight/`를 임시 폴더에 복사해 `/garmin-weight/` 경로로 서빙하고 같은 브라우저 프로필로 다시 연다.
- **Garmin 쪽 변경은 러너에서 확인한다.** 로컬에는 자격 증명이 없다.
- **요약 생성 결과 비교.** 현재 코드로 `--skip-garmin` 재생성한 결과는 `generatedAt`을 빼면 커밋된 파일과 완전히 같다. 리팩터링 전후 비교의 기준으로 쓸 수 있다.
