## 교대 규칙 (`source_rotation.py`)

- 매 조회는 출처 하나를 쓴다. 출처 목록을 섞어 한 바퀴에 한 번씩 꺼내고, 다 꺼내면 다시 섞는다(섞은 주머니). 한 출처에 연달아 몰리지 않고, 출처마다 호출이 1/4 수준이 된다.
- 꺼낸 출처가 실패하면 같은 조회 안에서 나머지 출처를 무작위 순서로 이어서 시도한다. 그래서 교대 조회가 대체 경로 역할도 한다.
- 공식 API 외 출처는 **3회 연속 실패하면 10분 쉰다.** 공식 API는 쉬지 않는다. runner 교체와 data.go.kr 오류 기록이 공식 결과를 기준으로 하기 때문이다. 공식 API가 연결 시간 초과 상태면 그 출처 차례의 조회는 최대 30초(목록 + 항목 폴백) 늦어진다.
- **소실·교체 재확인:** 대체 출처 응답에서 추적 중인 차량이 사라지거나 다른 차량으로 바뀌면 다음 출처로 한 번 더 확인한다. 공식 목록 API의 항목 재확인과 같은 이유로, 출처 하나의 누락이나 지연으로 도착을 확정하지 않으려는 것이다. 확인한 출처가 실패하면 처음 응답을 쓴다.
- **방금 도착한 차량 건너뛰기:** 도착 처리한 차량을 대체 출처가 10분 안에 다시 첫 차량으로 보여주면, 갱신이 늦은 것으로 보고 그 차량을 건너뛴다. 다음 차량이 있으면 그 차량을, 없으면 버스 없음을 쓴다. 출처마다 차량을 지우는 시각이 달라 같은 도착이 두 번 기록되던 문제를 막는다. 공식 API의 짧은 재등장은 기존처럼 추적을 다시 열고, 모델이 `quick_reappearance`로 거른다.
- **1정거장 전 멈춤 감지는 공식 값만 쓴다.** 공식 예측초가 150~200초에 멈추는 현상을 잡는 규칙이라, 분 단위나 따로 계산한 값이 끼면 매번 초기화된다. 대체 출처 관측은 감지를 시작하지도 지우지도 않는다. `backtest_safety.py`가 공식 행만으로 기준을 다시 만드는 것과도 같아진다.
- **기록 시각**은 자료를 준 출처의 요청 시작 시각이다. 앞 출처가 시간 초과로 30초 넘게 걸려도 늦게 받은 값을 조회 시작 시각으로 당기지 않는다. 다음 조회 예약은 조회 시작 기준이다. `api_request_started_at`은 조회 시작 시각, `last_poll`과 `safety.observation_ts`는 기록 시각이다.
- 카카오·네이버의 **후속 차량** 값이 이상하면 후속 차량만 버리고 첫 차량은 쓴다.
- **runner 교체:** 모든 출처가 실패하고 공식 API가 연결 시간 초과인 조회만 센다(기존과 같음). 대체 출처로 자료가 이어지면 교체하지 않는다. 교체 대기 동안 생기는 수집 공백이 더 크기 때문이다.
- **2차 정류장(06004):** 1차와 같은 출처가 공식이나 GBIS 웹일 때만 조회한다. 카카오·네이버 조회에서는 하지 않는다. 06004 도달은 GBIS 웹 노선 위치가 `route_pass_log.csv`에 따로 기록한다.
- **`route_signal_log.csv`**(07511 전 노선)는 공식 목록 API 조회에서만 쌓인다. 공식 API 차례가 줄어든 만큼 표본도 줄어든다.

## 기록과 모델

- `predict_log.csv`에 `source` 열을 추가했다(`official`/`gbis_web`/`kakao`/`naver`). 기존 행은 비어 있고 공식 기록으로 본다.
- **안전 모델 보정은 `official` 행만 쓴다**(`safety_model.calibration_source`). 출처마다 남은 시간 계산이 달라서다. 운행 구간(처음·마지막 관측, 소실 시각)은 모든 출처 관측으로 정한다. 감사 항목 `alternate_source_rows`에 제외한 행 수가 남는다.
- 실시간 안전 예측은 현재 출처 값에 공식 기준 보정을 그대로 적용한다. 출처별 보정은 자료가 쌓인 뒤 날짜를 분리해 비교하고 정한다.
- GBIS 웹 분 단위 값은 `predictTime1 × 60`이다. 2026-11-03 21:17:02 공식 목록 조회와 2초 뒤 GBIS 웹 정류장 응답을 07511의 20개 노선(같은 차량)으로 맞춰 봤다.
  - 분 × 60은 공식 초보다 **평균 14초 이르다**. 범위는 78초 이르게부터 37초 늦게까지다.
  - 내림과 맞은 노선이 13개, 올림과 맞은 노선이 5개다. 두 응답의 갱신 시점이 달라 어느 한 규칙으로 정해지지 않는다.
  - 평균적으로는 보수적(이른 쪽)이고, 늦은 쪽 최대 37초는 안전 보정 폭(수 분)보다 작다.
- `status.json`에 추가한 필드는 다음과 같다. 화면에는 "데이터 출처"로 보인다.
  - `data_source`: 이번 값의 출처. 큰 도착 시각 위에도 "도착 예정 · 카카오맵"처럼 표시한다(공식은 "공공 API", GBIS 웹은 "분 단위" 표시 추가).
  - `source_attempts`: 이번 조회의 시도 순서와 결과
  - `sources`: 출처별 당일 호출·성공·실패·연속 실패·쉬는 시각
  - `official_error_detail`: 대체 출처로 받았지만 공식 API가 실패했을 때
  - `source_errors`: 전 출처가 실패했을 때 대체 출처별 오류
- `daily_calls`(data.go.kr 900회 상한)는 공식 API 호출만 센다.

## 간격 (`bus_arrival.yml`)

| 항목 | 이전 | 지금 |
| --- | --- | --- |
| 조회 (추적 중 / 버스 없음) | 60초 / 120초 | `BUS_INTERVAL=30` / `BUS_IDLE_INTERVAL=60` |
| 게시 (평상시 / 버스 임박) | 300초 / 60초 | `BUS_PUBLISH_SECONDS=120` / 60초 그대로 (`BUS_URGENT_PUBLISH_SECONDS`) |
| GBIS 웹 노선 위치 | 매 조회 | 55초에 한 번 (`BUS_GBIS_WEB_MIN_GAP=55`) |
| 화면 재확인 | 60초 고정 | 다음 게시 예상 시각(게시 준비 + 게시 주기 + 25초)에 맞춤. 예정이 지나도 같은 자료면 20초 뒤 재확인, 최대 60초 |

- 임박 게시는 30초 조회 두 번에 한 번, 조회 직후 한다. Pages 배포 횟수는 늘리지 않는다.
- 예상 하루 공식 API 호출은 기존 약 380회에서 약 절반으로 준다. 조회 수는 두 배가 되지만 공식 차례가 1/4이다. 소실 재확인·항목 폴백 때문에 정확한 값은 운영 기록으로 확인한다.
- 코드 기본값은 기존과 같다: 출처 `official`만, 60/120초, 게시 300초, 노선 위치 매 조회. 테스트와 로컬 실행, 이전 워크플로 설정으로 시작한 세션은 동작이 그대로다.

## runner 접근 확인 (`source_probe.py`)

로컬 PC(국내망)에서 되는 출처가 GitHub Actions runner(해외 IP)에서 막힐 수 있다. `runner_diagnostics.py`는 DNS 주소만 남기므로, `source_probe.py`가 scrape.py와 같은 조회 함수로 출처마다 실제 요청·해석을 1회 해 본다.

- 판정: `ok`(해석까지 됨, 차량 유무와 무관) / `reachable`(접속됨, 모르는 차량번호·전 노선 차량 없음처럼 지금 쓸 값이 없음) / `failed`(시간 초과·연결·HTTP·형식 오류 = 막혔거나 응답이 바뀜).
- 오류 종류·HTTP 상태·소요 시간만 남긴다(URL·인증키·응답 원문 없음). 공식 API는 인증키가 있을 때만 1회 부른다.
- **수집 세션마다:** `bus_arrival.yml`이 세션 시작 때 1회 확인한다. 실행 화면 주석(`Bus source probe`)과 `bus-arrival-network-*` artifact의 `bus-arrival-sources.json`으로 남긴다. 실패해도 수집은 진행한다.
- **수집 전에 따로:** `bus_source_probe.yml`(workflow_dispatch, `bus-probe/**` 브랜치 push). runner 3대 × 3회(20초 간격)를 확인하고, 실패한 출처가 있으면 실행이 실패로 표시된다. 아무것도 커밋하지 않는다.

2026-11-04 10:02 KST 확인 결과([실행 41751211535](https://github.com/zzskm/zzskm.github.io/actions/runs/41751211535)): runner 3대 × 3회에서 공식·GBIS 웹 정류장·GBIS 웹 노선 위치·카카오·네이버 **5개 모두 9/9 성공**, 응답 최대 1.7초. 네이버는 로컬 회사망에서만 TLS 검사 때문에 실패한다(코드 문제 아님).

## 미검증

- runner IP와 지역은 실행마다 다르고, 공식 API는 10-27·10-29처럼 몇 시간씩 runner에서만 실패한 적이 있다. 위 확인은 그 시점의 runner 3대에 대한 결과다. 운영 중 상태는 `status.json` `sources`와 세션마다 남는 확인 결과로 본다. 막힌 출처는 3회 실패 뒤 10분씩 쉬고, 나머지 출처로 수집이 이어진다.
- 성남시청전면(06004)의 카카오·네이버 정류장 ID는 확정하지 못했다. 네이버 `5003272`는 야탑역.종합버스터미널(광역버스, 07643)이었다.

## 기타 수정

- `scrape.py`, `kakao_stop.py`, `naver_stop.py`는 `httpx` 로거를 WARNING으로 낮췄다. httpx는 INFO에서 요청 URL 전체를 남긴다. data.go.kr URL에는 `serviceKey`가 들어 있어, URL 인코딩된 키가 공개 Actions 로그에 찍히면 secret 가림 처리를 비켜 갈 수 있었다. 이전 실행 로그의 노출 여부는 확인하지 못했다.
