# 안전 출발 알림 신뢰성 후속 개선

입력은 `245ffa3690d2e45bf7a5524620d0de4fe6c5fb2c`의 공개 로그다. 기존 [SAFETY.md](SAFETY.md)와 [safety-backtest.json](safety-backtest.json)은 당시 결과로 보존한다. 이번 비교는 [engine-backtest.json](engine-backtest.json)에 별도로 기록한다. CSV와 운영 JSON을 PR에 포함하지 않는다.

## 예약 만료로 인한 누락

기존 일반 게시 300초와 안전 판단 유효기간 180초가 충돌했다. 예를 들어 API 잔여 1,200초, 3정류장 전, 안전 보정 -651초, 도보 300초, 추가 여유 60초이면 알림은 조회 후 189초로 예약되지만 발화 시점에는 `too_old`가 되어 사라진다.

게시 여부는 원시 API 잔여시간·거리 외에 **보정된 안전 도착 기준까지 900초 이하**인 경우도 포함한다. 기존 60초/120초 API 조회 간격은 바꾸지 않고 기존 조회 직후 게시한다. 일반 상태는 300초를 유지한다. 서버는 사용자별 도보/N 설정을 모르므로 이 조치만으로 모든 설정에 대한 전달을 보장하지 않는다.

이미 정상 자료로 생성한 예약은 이후 `too_old`/`api_error`/읽기 오류가 발생해도 최초 조회로부터 최대 10분 안에서 유지한다. 발화는 “예약 출발 경고 · 최신 정보 없음”으로 명확히 구분한다. 처음부터 오래된 자료만 본 경우에는 예약을 새로 만들지 않는다. 정상적인 차량 소실·교체, 시간대 변경, 사용자 건너뛰기·해제, 시계 오류에는 오래된 예약을 임의로 발화하지 않는다. API ETA가 이미 지난 예약도 출발 확정으로 부르지 않는다.

예약을 `busAlarm.v2.pending`에 보존하여 재로드 때도 복원하며, 기존 발화 원장과 같은 Web Locks 구간에서 저장한다. 원장은 차량 ID/N 단계별로 재발화를 막는다. Web Locks 미지원 브라우저, 10분 이상 공백, 탭/OS 완전 종료는 여전히 전달을 보장할 수 없다. 10분은 지연 자료로 무기한 경고하지 않기 위한 상한이며 통계로 검증한 도착 오차 보정값이 아니다.

## 모델이 불확실해졌을 때의 처리

- `trained_through`와 `training_days`는 실제 학습에 채택한 운행으로 계산한다. 최근의 부적합 운행이 오래된 모델을 최신으로 보이게 하지 않는다.
- 현재/미래 날짜, 잘못된 스키마, 유효한 전체 운행층 부족은 명시적인 `model_status`를 반환한다.
- 정상 모델이 14일보다 오래되었거나 학습 날짜 검증이 약한 이전 v1 모델이면, 기존 꼬리 보정을 **retained_margin**으로만 보존한다. 이를 최신 분위수 예측으로 표시하지 않고 평균 보정도 사용하지 않는다. 이전 -788초 여유가 고정 -240초로 갑자기 줄어드는 경로를 없앤다.
- 모델이 아예 없으면 고정 660초를 쓴다. 기존 전 운행 P05 -651초를 분 단위로 올린 초기 안전 여유다. 자료가 없어도 95%를 보장하는 값이 아니며 최초 차량 발견이 이미 늦은 경우를 해결하지 못한다. UI와 JSON에 표본 부족/모델 없음과 고정 11분 여유를 표시한다.
- 최신 P05/전체 운행 하한은 유지한다. 오래된 모델의 여유를 보존하는 것도 교통·노선 변화 이후의 커버리지 보장은 아니다.

## 사전 준비와 실제 출발 경고

시간대만으로 사전 알림과 실제 차량의 동일성을 확정할 수 없다. 그래서 시간상 후보가 하나여도 실제 차량의 발화 원장으로 사전 기록을 이전하지 않는다. 과거 운행은 **사전 준비** 안내이며 차량이 나타나면 “동일 운행 미확인”이라는 수동적 안내를 한다. 실제 안전 출발 경고는 차량 ID에 따라 별도로 한 번 판단한다. 준비 안내와 출발 경고는 목적이 다르며, 준비 안내 때문에 필요한 출발 경고가 억제되지 않도록 선택했다.

현재 알려진 후속 차량이 같은 시간대를 공유하거나 후보가 여럿이면 연결 안내도 하지 않는다. 실제 차량별 반복 알림 방지는 기존 원장이 계속 담당한다. 같은 요일 4일·휴일·운행 변동 제한은 유지한다. 정각/30분 경계 양쪽에 같은 반복 운행이 나뉘어 표본이 부족해지는 문제는 최대 15분 범위의 시각 묶음으로 보완했다. 하루에 여러 운행이 섞이면 사전 준비를 제한한다.

## 실제 엔진을 사용한 검증

`backtest_engine.py`가 수집 행과 소실 이벤트에서 게시 시나리오를 만들고, `replay_alarm.mjs`가 **운영 alarm.js 자체**를 1초 단위로 실행한다. 발화 조건, 원장, 최신성, 예약 유지를 Python으로 다시 구현하지 않는다. 비교 대상은 이전 커밋의 alarm.js를 별도 입력으로 실행한다. 엔진과 입력 파일의 SHA-256을 결과에 남긴다. 기존 Python 근사 재생은 이전 보고서 재현용으로만 보존한다.

날짜 전체를 분리한 최종 검증은 51운행(기존 보고서 뒤에 추가된 1운행 포함), 도보/N=5분·추가 여유 1분·공개 확인 지연 60초다.

| 조건부 대리 지표 | 이전 안전 알림 엔진 | 수정 엔진 |
|---|---:|---:|
| 놓칠 가능성 있음(구간 하한 초과, 알림 없음 포함) | 1/51 (1.96%) | 1/51 (1.96%) |
| 알림 누락 | 0/51 | 0/51 |
| 운행 전체 조기 커버리지 | 49/51 (96.08%) | 49/51 (96.08%) |
| 정류장 대기 평균 범위 | 354.7~413.5초 | 354.7~413.5초 |

기록된 51운행에서 추가 성능 향상을 주장하지 않는다. 이 기록에는 189초 만료와 같은 특정 실패 조건이 없었고, 그 조건은 별도의 생산 엔진 재생 테스트로 재현·방지했다. 처음 4개 날짜 이후의 각 날짜를 그 이전 날짜만으로 학습해 10개 날짜의 순차 검증도 실시했다. 10/7에는 가능한 놓침 20%, 누락 10%가 남아 있어 최종 5일의 수치만으로 운영 성능을 확정할 수 없다. 날짜별 결과와 0/60/120/180/300초 전달 지연 민감도는 JSON에 있다.

전체 운행 하한을 해제하는 연구 후보는 대기를 약 10.9초 줄였지만 커버리지가 96.08%에서 84.31%로 낮아졌다. 따라서 운영 보정을 완화하지 않는다. P10도 92.16%로 낮아 운영 기본 P05를 유지한다.

재생에서도 소실=통과라는 조건부 구간을 사용할 뿐 실제 도착 시각은 여전히 미측정이다. 게시 시각은 실제 commit/Pages 수신 이력이 아닌 시나리오이며, API 응답 실패가 CSV에 남지 않은 구간은 완전하게 복원할 수 없다. 사전 준비의 실제 운행 연결 정확도나 실제 OS 알림 도달률을 검증한 결과도 아니다. 평균 대기의 분모는 발화한 운행이며 놓친 운행의 대기는 0으로 계산될 수 있다.

## 배포 적용 확인

수집 세션은 첫 조회 전에 새 요약/학습을 생성한다. collector와 summary에 `runtime_schema_version: 2`, 모델 준비 상태, 학습일을 기록한다. 게시 준비 뒤 `verify_runtime.py`가 같은 스키마와 현재 관측에 대응하는 안전 예측을 확인한다. 부적합하면 게시를 실패시키며 복구 artifact에는 요약 JSON도 포함한다.

이 검사에서 `publish_prepared_at`은 Pages 배포 완료 시각이 아니다. 기존 긴 세션이 병합 이전 코드를 메모리에 보유하거나 새 실행이 아직 시작되지 않았을 수 있다. 공개 상태/요약의 스키마가 구형이면 “새 모델 적용 완료”로 보고하지 않아야 한다. 운영 파일을 강제로 재생성하거나 실제 수집 워크플로를 수동 실행하지 않았다. 병합 후 새 수집 실행과 공개 JSON 검사가 통과해야 운영 반영 완료다.
