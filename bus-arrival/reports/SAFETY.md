# 3100번 안전 출발 보정: 분석·운영·검증

분석 입력: `120a0873c5d2f9effbf06b6af242859122aeb14a`의 공개 로그. 원본 CSV와 현재 운영 JSON은 이 PR에서 변경하지 않는다. 재현 결과와 입력 SHA-256은 [safety-backtest.json](safety-backtest.json)에 있다.

## 데이터에서 확인한 문제

- 예측 3,531행: 차량 없음 1,712행, 차량 관측 1,819행. 추적 구간에 연결되지 않는 차량 관측 16행은 학습에서 제외한다.
- 종료 기록 142운행 모두 차량 ID + `first_seen_ts <= ts <= last_seen_ts` + 번호판으로 연결된다. 중복 예측, 중복 운행, 겹친 운행 구간, 번호판 불일치, 표본 수 불일치, 누락된 구간 끝점은 이 입력에서 각각 0건이다. 코드에는 각각의 검사와 회귀 테스트가 있다.
- `observed_arrival` 91건, `estimated_arrival` 48건, `vanished` 3건. 기존 `_classify_departure()`는 `last_predict <= 60`만으로도 observed로 부른다. **모든 예측 행의 `state_cd`가 비어 있어 실제 도착 확인 기록은 없다.** `arrival_confidence`도 계측 정확도나 보정 모델의 신뢰구간이 아니다.
- `est_arrival_ts = min(last_seen + last_predict, first_missing)`는 같은 API에서 나온 파생값이다. 이를 정답으로 다시 학습하면 순환 평가가 된다. 참고 비교에서 운행별 최악 오차의 P05는 -605초지만, 실제 도착에 대한 정확도를 뜻하지 않는다.
- `vanished`/긴 수집 공백 등 신뢰할 수 없는 3운행은 제외한다. 180초 안의 동일 차량 재등장 1건도 감지된다(이미 제외된 운행과 겹친다). 최종 조건부 구간 평가 대상은 139운행이다. 단일 관측 운행 등 짧은 추적은 따로 집계하며, 이를 장시간 정밀 추적으로 해석하지 않는다.
- 보조 정류장 기록 1,053행 중 1,041행이 같은 차량·추적 구간에 연결되고 12행은 연결되지 않는다. `same_veh_at_both`만 있는 로그로는 두 정류장 간 실측 이동시간이나 실제 도착을 알 수 없다. 이 로그를 도착 정답으로 사용하지 않는다.

### 도착 구간과 오차

신호가 없는 정상 소실은 `[마지막 차량 관측, 다음 정상 응답에서 처음 차량이 없는 시각]`을 **소실이 통과를 의미한다는 조건부 구간**으로 사용한다. 후속 응답이 없으면 종료 시각을 사용하되 180초보다 넓은 구간/수집 공백은 제외한다. 향후 `state_cd=1`이 있으면 마지막 신호의 `[t-60초,t]` 구간으로 별도 분류한다. 신호 역시 GPS 실측 정답으로 부르지 않는다. 운행 종료 로그에는 근거, 하한·상한, 최초 소실, 마지막 상태/거리 컬럼을 추가한다. 이전 컬럼과 reason 명칭은 호환성을 위해 유지한다.

오차 부호는 `조건부 도착 하한 - (조회 시각 + API 잔여초)`이다. 음수일수록 API보다 일찍 도착할 위험이 크다. 각 운행·층에서 **최악 오차 하나**만 표본으로 삼는다. 연속 조회를 독립 표본으로 세지 않는다. 같은 날짜의 운행 간 상관도 있을 수 있으므로 보고서에 검증 날짜별 위험률을 함께 기록한다.

전 기간 기술통계에서 마지막 정류장·잔여 300초 이하의 운행별 최악 오차 P05는 -271초(131운행), 잔여 600초 초과·마지막 정류장은 -788초(57운행)였다. 시간대별 P05도 17시 -788초, 19시 -563초 등 차이가 있지만 16시·18시는 20운행 미만이다. 시간대층은 분석에만 사용하고 작은 표본으로 더 세밀한 학습을 하지 않는다. 전 기간 기술통계는 검증 모델을 적합하는 데 쓰지 않는다.

## 모델과 임계값

`계산할 API 도착 시각 = last_poll + predict_sec`

`안전 도착 기준 = API 도착 시각 + 하위 꼬리 오차 보정`

`안전 출발 기준 = 안전 도착 기준 - 도보시간 - 추가 안전 여유`

`N분 전 알림 = min(안전 도착 기준 - N분, 안전 출발 기준)`

- 기본 P05. 정렬한 운행별 최악 오차에서 `floor((n+1)*alpha)` 순위(1부터)를 사용한다. 순위가 0이거나 서로 다른 운행이 20개 미만이면 고정 240초 여유다. 이는 60초 조회와 150~200초 정체에 대비한 초기 운영값이며 95% 보장이 아니다. `fit_model`도 운행 ID를 중복 집계하지 않는다.
- 잔여시간 `<=300 / <=600 / >600초`, 거리 `<=1정류장 / 나머지`로 나눈다. 층 표본이 부족하면 충분한 전체 운행층을 먼저 사용하고, 전체도 부족하면 고정 여유를 사용한다.
- 운행 하나가 여러 층을 통과하므로 층별 P05만으로 전체 경로 95%를 주장할 수 없다. **전체 운행의 최악 오차 P05보다 늦게 잡지 않는 공통 하한**을 적용한다. 층 추정이 더 보수적이면 그것을 쓴다. 이는 마지막 구간에서 뒤늦게 출발시키는 문제를 막는 대신 대기를 늘리는 명시적인 선택이다.
- 출발과 별도로 표시하는 보정 도착 예상은 운행별 조건부 구간 중점 오차의 평균으로 계산한다. **중앙값은 알림·출발 판단에 사용하지 않는다.** 평균 예상도 실측 도착 시각이 아니다.
- 마지막 1정류장, 잔여 150~200초, 최초값 대비 15초 이내의 값이 60초 이상 유지되면 별도 정체 보정으로 최초 정체 관측보다 안전 기준이 늦어지지 않게 한다. 앵커는 추적 상태에 저장해 게시/프로세스 재시작 때마다 뒤로 밀리지 않는다. 차량 교체·예측 변화·정류장 이탈 시 해제한다.
- 기본 추가 여유 60초, 사용자 설정 0~10분. 도보 0~60분과 기존 N분 전 설정을 함께 반영한다. 조기 보정으로 안전 출발 시점이 과거가 되어도 API ETA가 아직 미래라면 불확실성을 알리는 늦은 경고를 한 번 낸다. 기존처럼 이 경고를 '60초 미만'이라는 이유로 조용히 버리지 않는다.
- 운영 학습은 최근 42일 중 오늘 전체를 제외한 완료 날짜만 사용한다. 학습일이 당일·미래이거나 14일보다 오래되면 고정 여유로 돌아간다. UI/알림의 안전 판단은 **조회 3분 이내**에만 유효하다. 오래된 ETA 표시와 안전 판단을 구분한다.

P05/P10은 같은 날짜 분리로 비교한다. P10은 검증 커버리지 92%, P05는 96%였고 평균 대기 차이는 약 8초였다. 안전을 우선하는 사전 원칙과 전체 운행 하한을 기준으로 P05를 기본으로 둔다. 이 한 번의 작은 검증으로 최적 임계값이나 미래 성능을 확정하지 않는다.

## 날짜순 백테스트

학습 9일(9/28~10/12), 검증 5일(10/13~10/19), 검증 가능 50운행. 모델은 학습 날짜만 본다. 시나리오는 도보 5분, N=5분, 추가 여유 1분, 공개 후 브라우저 확인 지연 60초, 별도 push/Pages 지연 0초다. 두 방식 모두 같은 수집 관측 행에서 운행 전체 안전 도착 커버리지를 계산한다.

대기 평균의 분모는 알림이 난 운행(기존 46, 개선 50)이며 놓친 운행은 대기 0으로 들어간다. 그래서 기존의 짧은 대기를 좋은 품질로 해석하면 안 된다. 개선이 **대기시간까지 동시에 줄였다는 결과는 아니다**. 50건 중 남은 위험 1건은 최초 관측 시점부터 도착 하한까지 0초인 운행으로, 실시간 알림만으로 도보 5분을 확보할 수 없다.

게시 재현은 수집된 행에서 일반 300초, 임박 60초, 차량 최초 발견/소실 즉시 게시를 가정한 이상화 시나리오다. 기존 실행별 실제 commit/Pages/브라우저 수신 기록이 없으므로 실제 전달 지연·누락·사용자 행동을 복원한 결과가 아니다. 기존 `armedAt` 이전의 수동 알림 활성화나 건너뛰기도 재현하지 않는다(처음부터 활성화·탭 실행 중인 비교). 결과의 예측 커버리지는 계측 지연 가정과 별개지만 실제 놓침률은 달라질 수 있다.

추가 공개 확인 지연 0/60/120/180/300초 민감도는 JSON에 있다. 300초 지연에서는 개선 경로가 3분 최신성 검사를 통과하지 못해 모든 실시간 알림을 보류한다. 조회/게시 개선만으로 지연 상한을 보장하지 못한다. 96%는 소실 구간에 대한 표본 커버리지이며 실제 버스를 놓치지 않을 확률, 실측 95% 보장 또는 일자 간 독립성의 증거가 아니다.

## 게시·충돌·데이터 보존

- 기존 장기 GitHub Actions 세션과 Pages 구조를 유지한다. `predict_sec <= 900` 또는 2정류장 이내에는 **기존 조회 한 번이 끝날 때 게시**한다. 추적 중 60초, 차량 없음 120초의 API 조회 간격은 그대로다. 일반 상태 게시 300초, 첫 차량 인식·추적 종료 즉시 게시도 유지한다. 15분은 최대 N=20분 모든 사용자 설정에 대한 전달 보장이 아니라 도보/기본 알림을 위한 고정 운영 임계값이다. 20분 알림이나 긴 도보는 최초 인식이 늦으면 충족할 수 없다.
- 추가 API 요청은 없다. 두 정류장 모두 조회해도 6시간 연속 추적 약 720호출로 상한 900 이내다. 899회 상태에서 보조 조회로 901회를 만드는 기존 경계 문제도 수정한다. 무조회·일별 초기화·실행 사이 next_poll_ts 유지 테스트를 보존한다.
- 조회 요청 시작, API 응답 수신, 요청 소요시간, 게시 준비 시각과 그까지의 지연을 별도로 기록한다. `publish_prepared_at`은 **commit/push/Pages 배포 완료 시각이 아니다**. 실제 노출 시각과 API 원본 생성 지연은 여전히 미측정이다. Actions 대기열/cron, Pages 배포 합치기, CDN 캐시, 브라우저 확인 주기·절전·OS 알림/오디오 권한이 추가 지연을 만든다. 분당 커밋이 Pages 분당 배포를 보장하지 않는다.
- Actions concurrency는 유지하고 메인 직접 병합 없이 PR로 배포한다. 시작 동기화 실패 시 오래된 체크아웃으로 수집하지 않는다. rebase 충돌 때 한쪽 로그를 자동 선택하지 않는다. push 실패 후 수집을 계속해 runner 종료 때 데이터를 잃는 대신, 로컬 커밋을 보존하고 게시를 재시도하다 실패한다. HTTP 저속 타임아웃과 제한된 재시도로 350분 job 안의 종료 여유를 둔다.
- 실패 시 CSV/상태 JSON을 14일 artifact로 보존한다(서비스 키·환경 파일은 제외). GitHub 자체 중단·강제 timeout·artifact 업로드 장애에서는 이것도 보장되지 않는다. 오류 발생 시 artifact를 원본과 비교해 복구해야 한다.
- 자동 `trim_logs.py` 실행을 중단하여 원본 로그를 계속 보존한다. 학습은 42일로 제한한다. 공개 CSV 다운로드 용량은 장기적으로 늘어나므로 추후 원본을 보존하는 별도 아카이브 정책이 필요하다. 최근 기록은 기존처럼 summary의 30행을 우선 사용한다.

## 과거 운행 사전 알림과 기존 기능

사전 알림은 별도 사용자 선택이다. 같은 요일 최근 42일의 서로 다른 날짜 4개 이상, 30분 슬롯당 하루 1운행, 시각 분산 범위 15분 이내, 오늘의 알려진 휴일 달력, 평일을 모두 확인한다. 가장 이른 조건부 도착 하한보다 120초 빠른 기준을 사용한다. 현재 입력은 같은 요일 4일이 확보되지 않아 사전 알림이 제한된다. 표본 부족을 채우기 위해 다른 요일이나 미확인 휴일을 섞지 않는다.

사전 알림은 “실시간 차량 미확인”이라고 표시한다. API 오류/오래된 응답은 차량 없음으로 취급하지 않는다. 별도 날짜·슬롯 원장에 알린 N분 단계를 저장한다. 실시간 차량이 나타나고 시간상 후보 슬롯이 정확히 하나이며 알려진 후속 차량이 그 슬롯을 공유하지 않을 때 기존 차량 ID 원장으로 단계를 옮긴다. 확인은 화면 안내로 하고 같은 단계의 소리를 다시 내지 않는다. 모호하면 실제 차량 알림을 억제하지 않는다. 이 시간대 연결은 실제 배차/차량 ID를 사전에 안다는 뜻이 아니며, 미관측 후속 차량이나 예외 운행이면 다른 운행을 연결할 위험이 남는다. 새 N분 단계는 별도로 알릴 수 있다.

`alarm.js`는 순수 판단을 유지하고 UI는 저장·탭 잠금·OS 알림·소리를 담당한다. 기존 `assessStatus` 호출은 하위 호환으로 원시 API 기준이며 **실제 대시보드는 `safetyMode:true`**를 사용한다. 차량별 중복 원장, 시간대, N분 설정, 건너뛰기, 시각 알람, 타이머, 탭 복귀/worker, Web Locks, 오디오 해제 동작을 유지한다. 과거 원장도 같은 탭 잠금 안에서 읽고 저장한다. Web Locks 미지원 브라우저의 교차 탭 중복 방지는 기존과 같이 강하게 보장할 수 없다.
