# 대시보드 버스·일반 알람 분리 및 사용성 개선 계획

작성일: 2026-10-28

상태: **1–3단계 구현·검증 완료 / 4단계 일부 남음 / 배포**. 진행 결과는 아래 ‘구현 결과(2026-10-28)’와 [작업 기록](personal-dashboard.md)에 정리했다.

## 목표와 기본 결정

‘귀가 · 3100번 버스’에 함께 들어 있는 버스 기능과 일반 시각 알람·타이머를 각각 독립된 카드로 제공한다. 사용자가 지금 할 일, 다음에 울릴 알람, 알림을 받을 준비 상태를 바로 파악하도록 한다.

- 카드 이름: **버스 알림 · 3100번**, **알람 · 타이머**.
- 버스 카드의 켜기·끄기는 버스 알림에만 적용한다. 시각 알람은 개별 스위치로 관리하며 실행 중인 타이머는 별도로 취소한다.
- 브라우저 알림 권한과 소리 출력은 공통 상태다. 카드마다 별도 권한을 얻는 것처럼 표현하지 않는다.
- 기존 저장된 시각 알람·타이머·버스 설정과 원장을 이어 사용한다.
- 한 탭에서 동작하고, 버스·일반 알람이 동일한 평가 루프·보조 워커·소리 출력을 공유하도록 한다.

## 현재 구조에서 확인한 문제

실제 소스와 기존 운영 화면 캡처를 기준으로 정리했다. 사용자 행동 관찰 실험의 결과는 아니다.

| 현재 상태 | 사용자에게 생기는 문제 | 개선 방향 |
| --- | --- | --- |
| ‘버스 상세 · 알림 설정 · 타이머’ 아래에 시각 알람·타이머 생성 폼이 다시 접혀 있음 | 일반 알람을 찾고 시작하는 데 여러 단계 필요 | 독립 카드에 활성 목록과 빠른 시작 노출 |
| 버스 판단, 권한, 소리, 차량 상세, 이력이 긴 카드에 혼재 | 지금 출발할지와 설정 상태를 빠르게 구분하기 어려움 | 출발 판단을 앞에 두고 설정·이력을 단계적으로 펼침 |
| 버스 알림 켜짐과 OS 권한·소리 상태가 비슷한 버튼으로 반복 표시됨 | ‘알림 꺼짐’이 일반 알람에도 적용되는지 혼동 가능 | 버스 기능 스위치와 공통 출력 준비 상태를 분리 |
| 시각 알람은 시각 문자열 순으로 나열됨 | 오늘·내일·반복 요일을 반영한 다음 알람이 명확하지 않음 | 실제 다음 실행 시각을 요약하고 정렬에 반영 |
| 일반 알람도 버스 HTML을 받은 뒤 함께 초기화됨 | 버스 화면 HTML 로딩 실패가 일반 알람 사용까지 막음 | 일반 알람 화면과 실행부를 버스 HTML 로딩에서 독립 |
| 동일 배너에 알림 문구를 덮어쓰는 구조 | 여러 알림이 동시에 발생하면 앞선 알림 확인이 어려움 | 발생 출처와 미확인 항목을 보여 주는 공통 알림 영역 |

근거 파일: `dashboard.html`, `dashboard.js`의 `loadBus()`, `bus-arrival/index.html`의 `#clock-panel`, `bus-arrival/app.js`의 `runAlarm()`, `renderClocks()`, `showRing()`.

## 화면 배치

데스크톱은 다음 2열 배치를 기본안으로 한다.

| 왼쪽 | 오른쪽 |
| --- | --- |
| 오늘의 근무 | 버스 알림 · 3100번 |
| 알람 · 타이머 | 체중과 활동 |

모바일과 키보드·보조기기 읽기 순서는 **근무 → 버스 → 알람·타이머 → 체중**으로 맞춘다. DOM 순서도 이에 맞춰 조정한다. 카드의 숫자 장식은 이 순서에 맞추거나 제거해 시각 순서와 충돌하지 않게 한다.

현재 버스 카드의 긴 고정 배치를 해제하고, 기본 상태에서 버스 요약과 일반 알람에 빠르게 도달하도록 카드 높이와 간격을 조정한다. 좁은 화면에서 버튼·입력창이 자연스럽게 줄바꿈되도록 하고, 활성 알람 목록은 카드 안쪽 스크롤 대신 페이지 흐름으로 읽을 수 있게 한다.

## 버스 카드

기본 화면의 정보 우선순위:

1. **출발 판단**: ‘8분 뒤 출발’, ‘지금 출발’, ‘판단 보류’ 등 현재 상태와 필요한 행동.
2. **핵심 시각**: 출발 권장 시각, 도착 예상, 도보·추가 여유시간을 짧게 표시. 예측과 실제 관측을 구분한다.
3. **버스 알림 스위치와 다음 알림**: ‘버스 알림 켜짐’처럼 적용 범위를 명시한다.
4. **요약 정보**: 마지막 확인 시각·최신성, 좌석·남은 정거장·다음 버스를 짧게 표시한다.
5. **조작**: ‘도보·알림 설정’, 필요할 때 ‘이번 차량 제외’, 새로고침.

‘도보·알림 설정’은 한 번의 클릭으로 해당 폼을 열고 포커스를 이동한다. 관측 이력·그래프·판단 근거는 별도의 ‘버스 상세’로 제공한다. 사용자 판단에 필요한 오류·오래된 정보·출발 시각 경과 안내는 기본 화면에 남긴다.

데이터 조회 중, 수집 시간 외, 차량 없음, 오래된 자료, 조회 실패를 구분한다. 오래된 예측을 정상 카운트다운처럼 보이지 않도록 기존 판단 규칙을 유지한다. 일반 알람 카드의 실행 상태에는 버스 데이터 오류를 전파하지 않는다.

## 알람·타이머 카드

### 기본 화면

- 상단: **다음 알람**의 이름·시각·요일 또는 날짜와 남은 시간. 예약이 없으면 ‘등록된 알람이 없습니다’와 추가 버튼을 표시한다.
- 실행 중 타이머: 이름, 남은 시간, 종료 시각, 취소 버튼을 항상 표시한다.
- 빠른 시작: 기존 **5·10·15·30분** 버튼을 접힘 없이 노출한다. 한 번 누르면 바로 시작되고 생성 결과를 안내한다.
- ‘시각 알람 추가’와 ‘직접 입력’ 버튼으로 카드 안의 입력 폼을 연다.
- 등록된 시각 알람은 다음 실행 순서로 정렬하고 꺼진 항목은 뒤에 배치한다. 다음 실행 시각 계산은 기존 한국 시각 규칙을 따른다.

### 생성·수정 흐름

- 시각 알람: 시각 → 반복 선택 → 선택적 이름 → 저장. 새 항목의 기본 반복은 **한 번만**으로 제안한다. 기존 저장 항목의 평일·요일 설정은 그대로 읽는다.
- 반복은 ‘한 번만 / 평일 / 매일 / 요일 선택’을 명시적으로 선택하게 한다. 선택 해제만으로 반복 의미를 추측하게 하지 않는다.
- 저장 전에 ‘내일 08:00에 한 번’, ‘월–금 18:00’처럼 실제 실행 의미를 보여 준다.
- 버스 정보 함께 표시는 추가 옵션으로 제공한다. 새 일반 알람에서는 기본 해제하고, 기존 알람의 설정은 보존한다.
- 기존 항목에 수정 동작을 제공한다. 수정 시 항목 식별자는 유지하고 다음 발화와 원장을 일관되게 갱신해 이미 지난 알람이 즉시 재발화하지 않게 한다.
- 삭제 후 짧은 ‘되돌리기’ 기회를 제공한다. 복구 시 중복 발화가 생기지 않도록 기존 식별자·원장과 함께 처리한다.
- 실행 중 타이머 취소는 해당 항목에만 적용한다. 입력 오류는 해당 필드 근처에 표시하고 입력값을 유지한다.

## 알림 권한·소리·울림 UX

- 두 카드에서 참조하는 공통 준비 상태를 한 곳에 둔다. 정상 상태는 짧은 ‘알림 준비됨’ 요약으로, 미설정 상태는 구체적인 원인과 해결 버튼으로 표시한다.
- OS 권한 거부, 브라우저 미지원, 소리 활성화 필요를 구분한다. 권한이 없어도 등록은 가능하며 화면 알림만 가능한 상태임을 알려 준다.
- 소리 활성화와 테스트는 사용자의 명시적 클릭으로 실행한다. 저장이나 자동 새로고침이 반복 권한 요청을 만들지 않게 한다.
- 버스 알림을 끈 상태에서도 일반 알람·타이머가 동작한다는 점을 각 카드 상태로 분명히 보여 준다.
- 울릴 때는 접힌 영역 밖의 공통 배너에 **버스 / 시각 알람 / 타이머** 출처와 이름을 표시한다.
- 동시에 발생한 알림은 미확인 목록으로 유지한다. 같은 평가 시점에는 버스 출발 알림을 먼저 제시하고 나머지는 발생 순서로 보여 준다. 소리는 하나의 출력으로 관리한다.
- ‘현재 알림 확인’과 ‘전체 확인’을 구분한다. Esc는 현재 표시된 알림 확인에 대응한다. 표시되는 항목과 소리 중지 범위를 일치시킨다.
- 배너가 나타날 때 편집 중인 입력의 포커스를 빼앗지 않는다. 확인·삭제 후 포커스가 사라지지 않도록 다음 적절한 조작으로 이동한다.

탭이 열려 있어야 동작한다는 안내는 공통 도움말에 간결하게 둔다. 브라우저 절전에 의한 지연을 숨기거나 정확한 백그라운드 전달을 보장하는 문구는 사용하지 않는다.

## 시각 디자인과 접근성

- 기존 색상과 분위기를 이어 가며 카드 제목·여백·입력 필드·버튼 스타일을 통일한다.
- 강한 색은 현재 출발 판단과 실제 경고에 집중한다. 상태와 클릭 가능한 버튼을 모양·문구로 구분한다.
- 주요 조작은 최소 44px 높이를 목표로 하고, 작은 보조 문구도 모바일에서 읽기 쉽게 조정한다.
- 밝게·어둡게·시스템 테마에서 상태 색과 텍스트 대비를 확인한다.
- 색 외에도 텍스트·아이콘으로 상태를 전달한다. 모든 입력에 명시적인 레이블을 둔다.
- 키보드로 추가·수정·켜기·삭제·취소·알림 확인까지 가능하게 한다.
- 초 단위 카운트다운을 스크린리더가 매초 읽지 않게 하고, 생성 결과·오류·실제 발화만 알린다.
- 360px 화면과 200% 확대에서 가로 넘침과 조작 가림을 확인한다.

## 구현 접근

### 반응형 화면과 조작 반응성

| 화면 폭 | 배치·조작 목표 |
| --- | --- |
| 320–599px | 한 열, 바깥 여백 12–16px, 입력과 버튼 줄바꿈, 빠른 타이머 2×2 배치 |
| 600–959px | 한 열로 충분한 카드 폭 확보, 관련 입력은 두 열, 헤더 도구 줄바꿈 |
| 960px 이상 | 계획한 2열 카드, 최대 콘텐츠 폭 1280px, 카드 간격 20–24px |

숫자 크기는 카드 폭에 따라 유동적으로 조절한다. 확대·긴 이름·권한 오류 문구가 있어도 잘리거나 가로 스크롤을 만들지 않게 한다. 모바일 가상 키보드가 열린 상태에서도 저장·취소 버튼에 접근할 수 있게 한다.

- 클릭·키보드 입력 직후 눌림 또는 처리 중 상태를 표시한다. 네트워크 조회 중에도 다른 카드 조작은 가능하게 한다.
- 로컬 알람 생성·삭제·토글은 다음 화면 갱신에 반영한다. 저장 실패를 성공으로 표시하지 않는다.
- 데이터 재조회 중 기존 자료와 카드 크기를 유지하고, 최초 로딩에서만 최소 높이를 확보한 자리표시자를 사용한다.
- 초 단위 갱신은 변경된 텍스트만 수정한다. 목록·차트 전체 재생성으로 포커스·입력·스크롤 위치가 바뀌지 않게 한다.
- 접힌 상세 그래프는 필요할 때 렌더링하고, 숨겨진 문서의 시각 갱신은 줄인다. 알림 판정과 화면 갱신을 구분한다.
- 로컬 주요 조작은 입력부터 변경된 화면 표시까지 200ms 이내를 목표로 한다. 같은 기기·브라우저에서 각 조작 20회 측정의 중앙값과 상위 지연을 기록한다. 이는 실제 사용자 전체의 응답 속도를 보장하는 수치가 아니다.

### 심미성과 시각적 완성도

전체 방향은 **차분한 녹색·따뜻한 중립색을 사용하는 일상 도구**다. 버스 카드의 큰 진녹색 면적을 줄이고 네 카드의 표면·제목·정보 밀도를 통일한다.

| 요소 | 구현 기준 |
| --- | --- |
| 색상 | 배경·카드·입력 표면·경계선·주요 행동·주의·위험을 의미별 변수로 관리하고 Shadow DOM에도 동일하게 전달 |
| 정보 강조 | 출발 판단·다음 알람·남은 시간을 첫 시선에 배치, 단위·보조 설명은 한 단계 낮은 강조 |
| 타이포그래피 | 시스템 한글 글꼴, 본문 14–16px·보조 12–13px·카드 제목 16–18px를 기본 목표로 설정 |
| 숫자 | 고정 폭 숫자로 카운트다운 흔들림 방지, 주요 숫자와 단위를 기준선에 정렬 |
| 여백 | 4/8/12/16/24/32px 간격을 사용하고 같은 역할의 요소는 동일한 간격 적용 |
| 표면 | 카드 모서리 14–16px, 입력·버튼 8–10px, 얇은 경계선과 절제된 그림자로 계층 표현 |
| 버튼 | 주요 행동·보조 행동·위험 행동의 모양을 통일, 비활성·호버·눌림·포커스 상태 제공 |
| 아이콘 | 동일한 선 굵기의 작은 SVG 아이콘과 텍스트 레이블 사용 |
| 모션 | 상태 변화에만 120–180ms 색상·불투명도 전환 사용, 지속 점멸이나 초 단위 숫자 애니메이션 배제 |

모션 감소 설정을 존중한다. 일반 텍스트 대비 4.5:1을 디자인 목표로 확인하고, 밝은·어두운 테마별로 경고·비활성 상태까지 검토한다. 성공 메시지는 경고색 대신 차분한 성공색으로 구분한다.

시각 검토는 같은 테스트 자료로 360/768/1280px 화면을 캡처해 비교한다. 기본·빈 목록·여러 알람·긴 이름·오류·울림 상태를 포함하고, 제목 정렬·버튼 높이·줄바꿈·강조 순서를 확인한다. 320px와 200% 확대는 별도 넘침 검사에 포함한다.

### 모델·노력도 권장

전체 구현은 **GPT-6 Astra / High**, 비용 효율을 우선한 대안은 **GPT-6.1 Sol / High**를 권장한다. CSS·문구의 좁은 후속 조정은 Medium으로 진행할 수 있다. 동시 발화·잠금·원장 문제처럼 High에서 해결되지 않는 재현 가능한 문제가 있을 때 XHigh를 검토한다.

이 선택은 알림 실행부 분리와 기존 설정 호환을 포함한 작업 난도에 대한 판단이다. 공식 문서는 [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)를 복잡한 추론·코딩에, [Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)을 복잡한 코딩의 비용 효율적인 선택으로 안내한다. [노력도 가이드](https://developers.openai.com/api/docs/guides/deployment-checklist)는 코드 추론에 Medium/High를 사용하고 더 높은 노력도는 검증된 이득이 있을 때 선택하도록 안내한다. 모델이나 노력도를 자동 변경했다는 의미는 아니다.

### 코드 구성

핵심은 **화면은 두 카드, 버스·일반 알람 실행부는 한 개**로 구성하는 것이다. 기존 컨트롤러를 카드별로 두 번 마운트하면 폴링·워커·소리·알림이 중복될 수 있으므로 실행 수명주기를 먼저 정리한다.

1. 기존 `alarm.js`의 계산·원장 규칙을 재사용한다. `app.js`에서 저장·잠금·발화·소리·공통 알림 수명주기를 분리하고, 화면별 렌더링과 연결한다.
2. 일반 알람 카드의 마크업은 대시보드에 직접 제공한다. 버스 HTML 조회 성공을 기다리지 않고 알람 목록·타이머를 초기화한다.
3. 버스 Shadow DOM과 일반 알람 카드가 각자 자신의 요소를 조회하도록 뷰 경계를 만든다. 서로 다른 루트로 옮긴 요소를 기존 단일 `$()`로 찾는 구조에 의존하지 않는다.
4. 기존 단독 버스 페이지는 동일한 실행부와 뷰를 기존 화면 안에서 사용한다. 저장소 키, 여러 탭 잠금, 원장 중복 방지와 기존 사용 흐름을 검증한다.
5. 재시도·재마운트·페이지 복귀 시 이벤트 리스너와 평가 루프가 중복되지 않도록 초기화·정리 경로를 명시한다.
6. 일반 알람은 버스 데이터 없이도 평가한다. 버스 힌트는 정상 자료가 있을 때만 부가적으로 표시한다.
7. 문서 숨김 시 화면 갱신을 줄이되 알림 판정은 유지한다. iframe·외부 UI 프레임워크를 추가하지 않고 현재 메모리 절감 방향을 유지한다.

예상 변경 범위는 `dashboard.html`, `dashboard.css`, `dashboard.js`, `bus-arrival/app.js`, `bus-arrival/index.html`, 알림 실행부·뷰 모듈, 관련 테스트다. 모듈 이름과 정확한 분리 지점은 1단계에서 확정한다. 기존 근무시간 알림은 버스 스위치와 독립된 설정을 유지한다.

검증할 핵심 시나리오:

- 기존 저장된 반복 알람·타이머가 새 카드에 표시되고 재로드 후 유지된다.
- 버스 알림 꺼짐, 버스 HTML 로딩 실패, 버스 API 오류·오래된 데이터 상황에서도 일반 알람·타이머는 동작한다.
- 빠른 타이머는 한 번 클릭해 한 개만 생성되고 목록과 남은 시간이 바로 나타난다.
- 시각 알람은 자정·다음 날·요일 경계에서 다음 실행 안내와 실제 발화가 일치한다.
- 수정·삭제·되돌리기·타이머 취소 후 잘못된 발화나 중복 항목이 생기지 않는다.
- 버스·시각 알람·타이머 동시 발화 시 각 항목을 확인할 수 있고 알림이 덮여 사라지지 않는다.
- 기존 단독 버스 페이지와 대시보드를 함께 열 때 잠금·원장이 동일 발화를 중복 처리하지 않는다. 잠금 미지원 환경의 기존 한계도 구분한다.
- 접힘·숨김·재시도·페이지 복귀로 폴링·리스너·워커가 중복 생성되지 않는다.
- 권한 거부·소리 활성화 실패·저장소 실패가 해당 조작 근처에서 이해 가능한 문구로 안내된다.
- 360px 모바일, 데스크톱, 밝은·어두운 테마, 200% 확대, 키보드 입력과 포커스 복귀를 확인한다.
- 기존 근무·체중 기능과 버스 출발 판단·설정·차량 제외 회귀 테스트를 통과한다.
- 이전 메모리 비교와 같은 조건으로 결과를 재측정하고, 실행부 중복이나 설명되지 않는 증가가 없는지 확인한다. 기존 47% 절감 수치를 새 버전의 측정 결과로 재사용하지 않는다.
